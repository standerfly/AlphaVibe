# 外站四段票自動比價：機制研究與可行性評估

- 日期：2026-09-22
- 動機：PO 想在 STND 新增「機票查詢」分頁，自動掃描外站四段票找最低價，
  取代目前手動逐一輸入日期查價的作法
- 狀態：研究完成，**尚有一個決定性假設未驗證**（見第 5 節），不建議直接開發

## 1. 外站四段票是什麼

**外站票**＝不從自己居住地（台北）出發，而是從第三國城市（外站）出發的機票。
**四段票**＝一張票含四個航段，頭尾都在同一個外站。

標準結構（以曼谷為外站、巴黎為目的地）：

| 段 | 航線 | 用途 |
|---|---|---|
| 1 | 曼谷 → 台北 | 接駁段（可順便玩曼谷） |
| 2 | 台北 → 巴黎 | 主行程去程 |
| 3 | 巴黎 → 台北 | 主行程回程 |
| 4 | 台北 → 曼谷 | 接駁段 |

台灣旅客實際要的只是第 2、3 段，但因為航空公司對「非基地市場」放出的
轉機促銷價遠低於台北出發價，整張四段票常比單買台北→巴黎來回更便宜。
台北出發需求旺、票價硬；吉隆坡／曼谷／香港等地競爭激烈，促銷艙位開得多。

## 2. 價格差異來自哪些可控變數

這五項就是「自動掃描」真正要枚舉的搜尋維度：

1. **頭尾外站城市**——最大的價差來源。熱門便宜外站：吉隆坡、曼谷、香港、
   東京、首爾。原則是「哪裡便宜選哪裡」，沒有固定答案，必須實際掃過才知道。
2. **艙等代碼（booking class）配額**——計價邏輯殘酷：整票價格會被
   「四段中艙等最高（最貴）的那一段」拉上去。任一段低價子艙等售完，
   整張票強制跳階。這是價格跳動最不可預測的一環。
3. **日期（旺季／旺日）**——只要任一航段的出發日落在旺季或熱門節日，
   整張票總價就被拉高。
4. **中停次數**——多數超低價促銷票只含一次免費中停台北；想四段都中停
   會被加收約 USD 100–200 停留費。
5. **查詢方式**——必須用平台的「多城市（Multi-city）」功能查四段一本票，
   **分開搜尋會貴得離譜**。

## 3. 開票鐵律與風險（會影響 UI 要提示什麼）

- **第一段絕對不能 no-show 或取消**——第一段作廢，後面三段全部失效。
  這是外站票最硬的規則，不能用「棄搭第一段」來省事。
- 部分票規有 `NOT VALID FOR CIRCLE TRIP VIA NON-HUB CITY`，須經樞紐轉機；
  長榮特例要求第 1、4 段在台北轉機須於 24 小時內完成。
- **商務艙通常不適用**——商務艙促銷艙多帶
  `VALID FOR ROUNDTRIP ONLY. NOT PERMITTED ON MULTI-CITY`，一輸入多城市
  就跳 C/J 艙、票價翻倍。經濟艙才是外站四段票的甜蜜點。
- 隱藏成本：台北↔外站若非本票涵蓋需自費、外站簽證費、兩張獨立票之間
  延誤無銜接保障（後段航空無義務免費改簽）。
- 不適合請假彈性低、行程易變動的人——票規彈性換來的低價是用「不能改」買的。

## 3b. PO 提供的真實實例（2026-09-22，台北→布拉格）

同一天 PO 提供一張「跳區外站四段票」對照圖，是目前唯一的真實價格錨點。
「跳區」不是另一種玩法，就是本文機制的行話——利用 IATA 不同票價區域
（曼谷屬亞洲區、布拉格屬歐洲區）的價差套利。

| | 一般買法 | 跳區外站四段票 |
|---|---|---|
| 航段 | TPE-PRG 7/3、PRG-TPE 7/13 | BKK-TPE 7/2、**TPE-PRG 7/3**、**PRG-TPE 7/13**、TPE-BKK 9/8 |
| 票價 | TWD 44,794 | TWD 31,036 |
| 託運行李 | 2 × 23kg | 2 × 23kg |
| 哩程 | 6,732 | 8,586 |

**第 2、3 段與一般買法是完全相同的班機**（連 00:10 / 10:20 的時刻都一樣），
純粹因為前後包了曼谷兩段，票價就少 13,758（-30.7%）。

這張圖推翻了本模組原先的三個假設，皆已修正：

1. **必須自費買接駁票**——圖上警語：「第一段一定要搭乘！需再買 TPE-BKK
   單程機票」。真實成本＝四段票價＋台北→外站單程票價。原本只按票面價排序
   會系統性偏袒「票面低但接駁貴」的遠外站。已新增 `search_oneway()`／
   `estimate_connectors()`，`scan()` 改以 `total_cost` 排序。
2. **第四段可以丟到很遠的未來**——第 3 段 7/13 回台北，第 4 段 9/8 才飛回
   曼谷，相隔 **57 天**，用意是留給下一趟旅行當去程或直接棄搭。原本
   `ret_stays` 預設 `[0]` 完全掃不到。已在 CLI 加提醒並支援任意天數。
3. **查詢介面是荷蘭文版**（`Controleren en boeken`／`per persoon`／
   `Selecteren`），但報價為 TWD——暗示訂票地(POS)可能影響價格。原本寫死
   `gl=tw, hl=zh-TW`。已新增 `compare_pos()` 驗證此假設，快取鍵也加入
   gl/hl 避免不同 POS 的價格互相污染。

另兩個順帶修正的缺陷：
- **隔日轉機**：BKK 18:00 抵台北、TPE 隔日 00:10 飛 PRG，日期差 1 天但實際
  只隔 6 小時（仍在票規的 24 小時內）。`out_stays` 預設已改為 `[0, 1]`。
- **掃描順序**：原本外站是外層迴圈，額度中途用完只會拿到第一個外站的整月
  曲線。已改為日期優先、外站輪替（`interleave=True`），讓有限額度先橫向
  覆蓋所有外站。

驗證（2026-09-22 實跑）：`build_itineraries` 以
`out_stay=1, trip_day=10, ret_stay=57` 確實枚舉出圖上那張票的完整四段
（`BKK/07-02 → TPE/07-03 → PRG/07-13 → TPE/09-08 → BKK`）。

## 3c. 第二組實例：米蘭旅居型（2026-09-22，推翻搜尋空間預設）

PO 同日提供第二組對照圖（Skyscanner 系 App，長榮直飛），同一路線
`BKK-TPE / TPE-MXP / MXP-TPE / TPE-BKK`，**四個班機完全相同**，只有第 4 段
日期不同：

| 第4段日期 | 票價 | 結果筆數 |
|---|---|---|
| 2027-03-12 | **TWD 15,225** | 926 |
| 2027-03-24 | TWD 18,564 | 1,110 |

**只把第 4 段延後 12 天，貴 3,339 元（+21.9%）。** 第 4 段日期不是細節，
是主要價格槓桿之一——這也證實 3b 節第 2 點（第四段必須當成搜尋維度）。

### 真實參數 vs 原本的預設

| 維度 | 本實例真實值 | 原預設 | 落差 |
|---|---|---|---|
| 第1→2段間隔 | 15 天 | `[0, 1]` | 掃不到 |
| 第2→3段間隔（主行程） | **91 天**（米蘭旅居） | `[10]` | 差 9 倍 |
| 第3→4段間隔 | 1 或 13 天 | `[0]` | 掃不到 |

原本假設的「十天觀光」情境與真實玩法差了一到兩個數量級。

### 由此產生的介面重新設計

原本的 `build_itineraries()`「給月份、掃整月出發日」假設行程未定。但本實例
顯示**主行程（第 2、3 段）是使用者已經決定的**——12/10 去米蘭、3/11 回，
那是旅行本身。真正該掃的是：外站、第 1 段提早幾天、第 4 段延後幾天。

已新增 `build_itineraries_fixed_trip(destination, outbound_date,
return_date, ...)` 對應這個情境，CLI 為 `--outbound` / `--return-date`。
原本的月掃描模式保留給「行程還沒定」的情況。

### 分層貪婪掃描（額度現實）

固定行程模式的全組合是 8 外站 × 22 lead × 22 trail ＝ **3,872 次**，
免費層 250 次/月差了 15 倍。已新增 `scan_layered()`，三層各只動一個維度：

| 層 | 動作 | 額度 |
|---|---|---|
| 1 | 固定 lead/trail，比所有外站 | 8 |
| 2 | 取最便宜 top_k 外站，掃 lead | 2 × 22 = 44 |
| 3 | 取第 2 層最佳，掃 trail | 2 × 22 = 44 |
| | **合計** | **96 次**（省 98%，塞得進免費額度） |

**已知取捨**：貪婪法假設各維度近似獨立，可能錯過「某外站只在特定 lead 下
才最便宜」的交互作用。維度本身影響已證實（第 4 段單獨 21.9%），維度之間
是否獨立**尚未驗證**——拿到 API key 後值得用小範圍全掃比對一次。

### 順帶修正

預設 `lead_days` 原本憑空定為 0-14，**差一天就漏掉本實例的 lead=15**。
已改為 0-21 並用實例值寫成測試釘住（`test_defaults_cover_the_po_example_values`）。
教訓：預設值要能涵蓋已知真實案例，不是拍腦袋。

驗證（2026-09-22 實跑）：兩組圖的航段皆可完整重現——
`BKK/11-25 → TPE/12-10 → MXP/03-11 → TPE/03-12 → BKK`（$15,225）與
`… → TPE/03-24 → BKK`（$18,564）。

## 5. 決定性未驗證假設（開發前必須先測）

**所有中文教學文章都指定用 Skyscanner／Trip.com／Airpaz 的多城市功能查四段票，
沒有任何一篇提到 Google Flights。**

而我們唯一能穩定取得的代抓資料源是 Google Flights。四段票的低價高度依賴
艙等代碼組合（第 2 節第 2 點），不同平台背後的 GDS 查詢與艙位組合邏輯不同，
**Google Flights 的四段 multi-city 報價未必等於 Skyscanner 查到的便宜價**。

驗證方法（成本：免費額度內，約 6–10 次查詢）：
1. 直接用第 3b 節的實例當基準（BKK/07-02→TPE/07-03→PRG/07-13→TPE/09-08，
   已知 Skyscanner 系價格 TWD 31,036），再補查 1–2 組其他外站
2. 用 SerpApi `type=3` 查完全相同的航段與日期
3. 比對價差：
   - 差距 < 10% → Google Flights 路線可行，照原計畫開發
   - 差距 > 10% → 必須改用 Sky Scrapper（代抓 Skyscanner），成本與穩定度重估

**在這個驗證通過之前不要開始寫分頁**，否則可能做出一個查得到價格、
但永遠比手動查貴的工具。

## 6. 零成本方案（PO 2026-09-22 明確要求：不要花錢）

**結論：不用花錢也做得到**，前提是用分層掃描而非全組合掃。

### 免費額度的現實

SerpApi 免費層：**250 次/月、50 次/小時、註冊不需信用卡、不會自動轉付費**
（2026-09-22 查證）。關鍵數字對照：

| 做法 | 查詢量 | 免費額度夠嗎 |
|---|---|---|
| 固定行程全組合掃（8 外站 × 22 × 22） | 3,872 | ✗ 差 15 倍 |
| **分層貪婪掃描**（見 3c 節） | **96** | ✓ 一個月可跑 2 趟規劃 |
| 月掃描模式（8 外站 × 30 天，行程長度固定） | 240 | ✓ 剛好，但一個月只能跑 1 次 |

個人旅行規劃一年不會超過幾趟，每月 2 次規劃額度綽綽有餘。額度不夠時的
備案是換供應商而非付費——Bright Data 免費 5,000 credits/月（見第 4 節）。

### 額度守衛（已實作）

免費額度是「本月用完就沒了」的硬限制，而且**跨次執行會累計**——只靠單次
執行的 `--limit` 擋不住「今天跑一次、明天再跑一次」的累計超額。因此：

- 用量持久化在 `data_dir/flight_usage.json`，每打一次 API 就即時記帳
  （中途中斷也不會漏記），按自然月自動歸零
- `_query_batch()`／`scan()`／`scan_layered()` 在額度耗盡時立即停止
- CLI 在**實際發出請求之前**就擋下超額操作，並提示改用 `--layered`
- 快取命中不扣額度，所以反覆測試同一組查詢不會白燒
- `--quota 0` 可解除限制（換用額度更大的供應商時）

2026-09-22 實跑驗證：全組合掃（3,872 次）被擋下並提示分層方案；額度用盡
情境被擋下；兩者**皆未發出任何 API 請求**。

### 仍需注意的非金錢成本

限速 50 次/小時 → 分層掃描 96 次約需 2 小時。這是時間成本不是金錢成本，
但代表「手動觸發、即時拿結果」的體驗做不到，需要背景執行＋完成後通知。

## 8. 零成本查價路徑（2026-09-22 實測，重大發現）

PO 要求不花錢。除了免費 API 額度之外，還有一條**完全不需要 API key、
不需註冊、不消耗任何額度**的路徑：直接構造查詢網址，人點開就看到報價。

### 實測結果

| 方式 | 結果 | 證據 |
|---|---|---|
| Skyscanner 單程路徑 `/transport/flights/nrt/tpe/261207/` | ✓ 可用 | HTTP 200，標題「Skyscanner 上從東京到台北的便宜機票」 |
| Skyscanner 來回路徑（兩個日期） | ✓ 可用 | HTTP 200 |
| Skyscanner 四段路徑（串接四組） | ✗ **404** | 標題「找不到網頁」 |
| Skyscanner `flights-multi-city/` 路徑 | ✗ **404** | 標題「找不到網頁」 |
| Skyscanner referrals API `multicity` endpoint | ✗ **只讀第一段** | HTTP 200 但標題變成「Cheap flights from Tokyo to Taipei」 |
| **Google Flights `tfs` 參數** | ✓ **四段可用** | 見下 |

**結論：Skyscanner 的多城市搜尋不是網址可表達的**（前端狀態，非 URL 驅動）。
四段票連結只能用 Google Flights。

### Google Flights `tfs` 編碼（已實作於 `google_flights_url()`）

`tfs` 是 base64url 編碼的 protobuf（無 padding）：

```
Info.data       (f3, repeated)   每個航段
  FlightData.date        (f2)    "YYYY-MM-DD"
  FlightData.from_flight (f13)   Airport{name=f2}
  FlightData.to_flight   (f14)   Airport{name=f2}
Info.seat       (f9)    1=經濟 2=豪華經濟 3=商務 4=頭等
Info.passengers (f8)    成人數
Info.trip       (f19)   1=來回 2=單程 3=多城市
```

網址：`https://www.google.com/travel/flights?tfs=<base64>&hl=zh-TW&gl=tw&curr=TWD`

### 四段票網址的驗證證據（2026-09-22）

以 `NRT/12-07 → TPE/12-10 → PRG/12-22 → TPE/12-23 → NRT` 實測：

- HTTP 200
- 四個航段日期**全部**出現在頁面：12-07（11 次）、12-10（11 次）、
  12-22（8 次）、12-23（8 次）
- 三個機場代碼全部出現：NRT 38 次、TPE 73 次、PRG 36 次

- 對照組：同樣參數的單程網址標題為「臺北市到布拉格」，NRT 僅出現 2 次
  → 證明四段確實被完整解析，不是只讀第一段

該 tfs 值已寫成測試 `test_tfs_matches_the_url_verified_against_google`
釘住，編碼被改動會先失敗。

### 這條路徑的定位

- **立即可用**：在 API 資料源假設（第 5 節）驗證完成前，先用連結人工比價
- **額度用盡的備援**：免費額度用完時仍能查
- **驗證工具**：拿同一組航段的連結報價，對照 API 回傳值，就能直接檢驗
  第 5 節那個「Google Flights 查不查得到 Skyscanner 便宜價」的假設
- **限制**：只能人工點開看，無法自動批次比價與排序——自動化仍需 API

### `hl`／`gl`／`curr` 可切換訂票地

同一組航段改 `gl=nl&hl=nl&curr=EUR` 就是荷蘭版介面——正好對應 3b 節
PO 實例的荷蘭文截圖。這讓 POS 假設也能零成本人工驗證，不必先燒 API 額度。

## 9. 需求澄清：日期是輸出，不是輸入（2026-09-22，PO 二次澄清）

> 「日期才是我最困擾的、需要你幫我解決的。我想要的是，你找到便宜的機票，
> 然後我再看時間是否適合。」

這推翻了第 3c 節的固定行程模式假設。正確流程是：**先找便宜時段 →
PO 再判斷時間合不合適**，而不是先給日期再查價。

### 問題：搜尋空間爆炸

日期未定時，要掃的是「未來半年 × 外站 × 行程長度 × 前後段偏移」：

    180 天 × 7 個日本外站 × 3 種行程長度 × 2 × 2 ≈ 15,000 次查詢

免費額度 250 次差 60 倍；零成本連結路徑也不可能讓人點一萬五千次。

### 零成本路徑為何無法自動化（實測結論）

Google Flights 四段票網址雖然可用（第 8 節），但**頁面原始碼不含價格**
——2026-09-22 實測：來回票頁面 1,944,383 bytes，含「價格走勢」「最低價」
字樣與 3 個 `AF_initDataCallback` 區塊，但**找不到任何實際票價數字**，
價格由後續 XHR 載入。要自動取價就得跑 headless browser，超出合理範圍。

**所以零成本路徑只能產生連結給人點，自動比價必須用 API。**

### 解法：兩階段策略（已實作）

關鍵發現：SerpApi 的 **`google_flights_deals` engine 支援日期範圍**
（`outbound_date=2027-02-01,2027-02-28`）與行程長度範圍
（`trip_length=10,14`）——**一次查詢涵蓋整個月**，而非逐日查詢。
限制是它只支援 type=1/2，**不支援 multi-city**。

因此分兩階段（`plan_cheap_trip()`）：

| 階段 | 動作 | 額度 |
|---|---|---|
| 1 | 用 Deals API 逐月掃主行程（台北↔目的地），找便宜時段 | 每月 1 次 → 半年 6 次 |
| 2 | 取最便宜的 top_dates 組日期 × 各外站，查四段票 | 5 × 7 = 35 次 |
| | **合計** | **41 次**（免費額度內） |

**啟發式前提**：主行程便宜的時段，整張四段票也傾向便宜——因為只要任一
航段落在旺季，整票總價就被拉高（第 2 節第 3 點）。前提合理但**尚未實證**，
拿到 key 後應抽驗：挑一個階段 1 判定為貴的日期也查四段票，確認確實較貴。

**另一個未驗證點**：`arrival_id` 在 Deals API 官方參數表中沒有記載（只
出現在回應範例），該 engine 可能其實是「找便宜目的地」模式。
`search_deals()` 因此照常傳送 `arrival_id`，但**額外以回應中的目的地
欄位再過濾一次**，並寫了測試
（`test_filters_out_other_destinations`）確保便宜的錯誤目的地不會混入。

### PO 的兩個選項

1. **零成本、立即可用**：開 Google Flights 台北↔目的地來回票連結，點
   「價格圖表」看未來 6 個月的價格曲線，自行挑出便宜週；再把日期給我，
   我產生該時段的四段票連結（第 8 節）。缺點是人工。
2. **自動化**：註冊 SerpApi 免費帳號（250 次/月、不需信用卡），
   `plan_cheap_trip()` 41 次額度就能跑完半年掃描並排序輸出。

## 10. `--plan-trip` 實作與端到端驗證（2026-09-22，PO 選定方案 B）

### 實測輸出（假資料）


### 端到端測試抓到的兩個缺陷（皆已修）

1. **殘缺的第一個窗口**：從「今天」起算時，若當月只剩 9 天，第一個查詢
   窗口就是 `2026-09-22,2026-09-30`——白花一次額度在最不可能便宜的近期，
   還少掃一個完整月。已加 `MIN_FIRST_WINDOW_DAYS = 14`：起始月剩不到
   14 天就跳到下個月 1 號，確保 N 個窗口都是完整月份。
2. **接駁估價漏記額度**：`estimate_connectors()` 呼叫的
   `search_oneway()` 沒有記帳（單筆查詢函式一律由批次呼叫端負責記帳，
   但這支批次函式漏了），導致實際打了 34 次、額度卻只顯示 27——**額度
   守衛會因此低估用量而超支**。已在 `estimate_connectors()` 補上
   `record_usage()`、額度守衛與快取判斷，修正後數字對上 34／250。

兩者都只有跑端到端才看得出來：單元測試各自通過，缺陷出在組合處。

## 12. 封鎖風險調查與節流設定（2026-09-22，PO 要求先查再定頻率）

### robots.txt 第一手查證

**Google**（`https://www.google.com/robots.txt`，263 行）：

```
Disallow: /travel/flights/booking
Disallow: /travel/flights/s/
Disallow: /travel/flights/search
```

**但沒有單獨的 `Disallow: /travel/flights`**，也沒有 `Crawl-delay` 指令或
萬用參數規則。我們使用的 `/travel/flights?tfs=...` 路徑**未被 robots.txt
禁止**（已用 `grep -nx` 逐行確認）。注意：robots.txt 允許 ≠ ToS 允許，
Google ToS 對自動化存取另有規定，這是風險而非豁免。

**Skyscanner**（`https://www.skyscanner.com.tw/robots.txt`，393 行）：

```
Crawl-Delay: 2
Disallow: /transport/*
```

**`/transport/*` 正是我們產生連結用的路徑** → Skyscanner **不可程式化
抓取**。`skyscanner_url()` 只能用於產生連結給人點（人工瀏覽不受
robots.txt 約束），絕不可拿去餵爬蟲。此限制已註記在該函式 docstring。

### 社群實務速率

公開資料沒有明確閾值。業界經驗值：單一 IP 的長期有效速率從
**每小時 3–5 次**（保守）到 **100+ 次**（視 IP 品質）不等；
單一 IP 高頻必被封，一兩次則幾乎不會。

### 壓力測試（2026-09-22 實測）

15 次連續查詢，間隔 **5–11 秒隨機**（固定間隔本身就是機器人特徵）：

```
成功 14 / 無結果 0 / 被擋 0 / 失敗 1（單次逾時）
總耗時 3.6 分鐘，平均 5.4 秒/次
```

**零封鎖跡象**，無 captcha、無異常流量警告。唯一失敗是第 7 次逾時
（25 秒內等不到「整趟行程」），其後 8 次全部正常 → 判定為偶發逾時而非
封鎖，但需要重試機制（失敗率 1/15 ≈ 6.7%）。

### 採用的節流設定

| 參數 | 值 | 依據 |

| 查詢間隔 | 5–11 秒隨機 | 壓測驗證無封鎖；隨機化避免規律特徵 |

## 14. 實測封鎖閾值與軟封鎖形態（2026-09-22/23，重要教訓）

```

[21-36/36] 連續 16 次全部 timeout 30.3s
```

### 教訓一：軟封鎖以「逾時」形態出現，不是 captcha

原本的封鎖偵測 `BLOCK_RE` 只認 captcha／unusual traffic／異常流量等
明確字樣。但 Google 的實際手法是**讓請求靜默逾時**——`blocked` 旗標
因此始終為 `false`，程式毫無所覺地繼續打了 16 次，只會加深封鎖。

**修正**：`flight_scraper.js` 新增 `SOFT_BLOCK_THRESHOLD = 3`，連續
失敗 3 次即視同被擋、立即中止，並以 `soft_blocked` 旗標與明確封鎖頁

## 20. 「每日 25 筆」是錯的——限制是速率（2026-09-23，PO 質疑後查證）

PO 質疑「每天只能跑約 25 筆」是猜測還是有證據。**是猜測**，而且方向錯了。

### 快取時間戳（硬證據）

| 時段 | 筆數 | 速率 | 結果 |
|---|---|---|---|
| 2026-09-22 23:41–00:04（23 分鐘） | 20 | **52 筆/小時** | 被擋 |
| 2026-09-23 08:58–09:04（**7 分鐘**） | 24 | **205 筆/小時** | 被擋 |

00:04 被擋、08:58 已能查 → 恢復時間 **≤ 8.9 小時**。

### 我的錯誤

觀察到的事實只有「約 20–25 筆後被擋」。我自己加上「每天」這個限定詞，
還把它實作成 `DAILY_BROWSER_LIMIT = 25` 與**跨日歸零**的邏輯——
「跨日」完全沒有證據支持，兩次被擋都發生在短時間密集查詢之後，
與「日界線」毫無關係。

業界經驗值是每 IP 每小時 3–5（保守）到 100+（好 IP）。我們跑
205 筆/小時，遠超上限；連 52 筆/小時也被擋。**限制更可能是速率。**

### 修正

改為**滾動小時速率限制**（`HOURLY_BROWSER_LIMIT = 20`）：
`flight_browser_usage.json` 改記每筆查詢的時間戳而非單純計數，
`read_browser_usage()` 只計最近一小時，並新增
`seconds_until_quota_frees()` 算出還要等幾分鐘才釋出名額
（而不是含糊地說「明天再來」）。CLI 參數 `--daily-limit` → `--hourly-limit`。

**20 筆/小時仍未驗證**——沒有「以此速率連跑數小時不被擋」的實測，
它只是遠低於已知被擋值（52）的保守推估。不要當成已知安全值。

### 教訓（同一天第三次同類錯誤）

第 14 節：15 筆壓測通過 → 誤以為無封鎖風險。
第 18 節：24 筆連續成功 → 誤以為「閾值是假象」。
第 20 節：觀察到 25 筆被擋 → 擅自補上「每天」。

三次都是**從不足的樣本外推出過強的結論**。可觀察的事實與推論之間要
明確分野：「觀察到 X」不等於「規則是 X」。
