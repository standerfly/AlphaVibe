# Spec Kit Input: 機票價格追蹤與通知

**Status:** Accepted
**Source Product Spec:** ../../product-spec.md
**Source Scope Decision:** ../../scope-decision.md
**Spec Feature Slug:** flight-price-tracking
**Handoff Order:** 2

## Feature Summary

讓機票查詢條件成為可持久追蹤的對象：依設定頻率自動重掃，當最低四段票價
跌破使用者設定的目標價時，主動以 Telegram 通知。並在重掃連續失敗時標示
資料過期，避免以過時價格誤發通知。

## Actors

- 個人使用者：設定重掃頻率與目標價、接收通知
- 系統排程：依頻率觸發重掃、判定達標、送出通知

## Problem and Goal

機票價格會變動，使用者不可能天天手動重查。目標是讓系統定期自動重掃已建立
的追蹤條件，並只在真的跌破目標價時主動通知，避免使用者需要持續盯著頁面。

## In Scope

- 重掃頻率設定（預設每週一次）
- 多個追蹤條件錯開到不同日執行，避免同時段累積觸發速率上限
- 自動重掃排程（比照既有 launchd 排程慣例）
- 達標判定：以**四段票價**為基準（不含接駁估價）
- Telegram 達標通知（複用既有推播基礎設施），內容含條件、價格、日期組合、連結
- 資料過期標示：超過 2 個重掃週期未成功更新即標為過期
- 過期狀態下不得以舊價觸發通知
- 追蹤條件的狀態呈現（待掃／排隊中／掃描中／部分完成／已完成／已達標／資料過期）

## Out of Scope

- 分頁骨架與查詢條件 CRUD（屬 flight-scan-page）
- 掃描演算法本身（屬 flight-scan-page）
- 價格趨勢圖與歷史走勢分析
- 「現在該買了嗎」的建議邏輯
- 重掃失敗的通知（MVP 僅 UI 標示過期）

## User Scenarios

1. 使用者設定目標價 NTD 38,000、頻率每週一次。某次重掃後最低四段票價為 NTD 37,265，
   收到 Telegram 通知，內容含日期組合與查價連結。
2. 四段票價 NTD 37,500、接駁估價 NTD 6,000（總成本 NTD 43,500）、目標價 NTD 38,000
   → 仍觸發通知（以四段票價判定）。
3. 追蹤條件連續兩週重掃失敗，狀態標為資料過期；即使上次價格低於目標價，
   也不發出通知。
4. 使用者建立第二個追蹤條件，系統將其排在與第一個不同的星期日執行。
5. Telegram 推播失敗，重試兩次後放棄，UI 標示「通知未送達」，但掃描結果
   正常保留。

## Functional Requirements

對應 product-spec 的 FR-12～FR-14。關鍵可測條件：
- 兩個追蹤條件不會排在同一天
- 達標判定使用四段票價，接駁估價不參與
- 過期狀態下即使舊價低於目標價也不發通知
- 通知失敗不影響掃描結果的保存
- 狀態轉換符合 supporting-artifacts/workflow-and-states.md 的狀態機

## Success Criteria

- 使用者不需手動重查即可在價格達標時收到通知
- 不會收到基於過期資料的錯誤通知
- 自動重掃不因速率上限而持續失敗（多條件錯開後，單日查詢量在配額內）

## Constraints and Assumptions

- 相依 flight-scan-page 先完成（掃描與資料層）
- 重掃頻率受速率上限約束：單一條件含 2 外站 × 8 日期＝16 筆已接近單時段上限，
  故高頻重掃不可行
- 排程須比照既有 `~/Library/LaunchAgents/com.alphavibe.*.plist` 慣例
- 通知複用既有 Telegram 推播基礎設施，不另建通道
- 部分完成（Partial）狀態仍可觸發達標通知（已查到的價格是真實的），
  但資料過期（Stale）狀態不可
- **貨幣統一 NTD**：目標價與通知內容皆以 NTD 表示

## Source Decisions

- 達標判定以四段票價為準，接駁估價僅供參考顯示
- 預設每週重掃，多條件錯開到不同日
- 資料過期時不得以舊價觸發通知
