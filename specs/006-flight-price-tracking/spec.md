# Feature Specification: 機票價格追蹤與通知

**Feature Branch**: `006-flight-price-tracking`
**Created**: 2026-09-23
**Status**: Draft
**Input**: `docs/spec-intake/flight-search/spec-kit-inputs/flight-price-tracking/speckit-input.md`（Accepted，handoff order 2）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 不必手動重查就能追到降價 (Priority: P1)

使用者已經建立好查詢條件（005 完成的功能），但機票價格會變動——他不可能
每天手動點「重新掃描」。系統應依他設定的頻率自動重掃，並把結果更新到
既有的結果表，使用者下次打開分頁就看到最新價格。

**Why this priority**: 這是本功能存在的理由。沒有它，使用者得靠自己記得
回來點按鈕；有了它，即使沒有通知功能，「打開就是新的」本身已有價值。

**Independent Test**: 設定一個條件的重掃頻率，確認排程到期時系統自動執行
掃描並更新結果與時間戳，全程不需使用者操作。

**Acceptance Scenarios**:

1. **Given** 一個重掃頻率為每週一次的條件，**When** 排程到期，
   **Then** 系統自動執行掃描並更新結果，無需使用者操作。
2. **Given** 使用者建立第二個條件，**When** 系統安排其重掃日，
   **Then** 兩個條件被安排在不同日執行，不在同一天累積查詢量。
3. **Given** 某條件的所有組合都已在查價快取中，**When** 自動重掃執行，
   **Then** 不發出任何外部查詢，結果與時間戳照常更新。
4. **Given** 自動重掃執行中遇到速率上限，**When** 本時段配額用盡，
   **Then** 完成可執行的部分、保留已完成結果，剩餘留待下次排程或手動觸發。
5. **Given** 使用者在分頁上調整某條件的重掃頻率，**When** 儲存，
   **Then** 下次排程依新頻率執行。
6. **Given** 任一條件，**When** 使用者檢視分頁，**Then** 可看到該條件的
   下次預定重掃時間與上次成功更新時間，不需自己推算。

---

### User Story 2 - 跌破目標價時主動通知 (Priority: P2)

使用者為條件設定了目標價。當某次重掃後最低的**四段票價**跌破該目標，
系統主動用 Telegram 通知他，內容要足以讓他直接判斷要不要行動——
價格、日期組合、外站、以及可直接開啟的查價連結。

**Why this priority**: 這是「主動」的部分，價值高但依賴 US1 的自動重掃
先成立。US1 單獨已可用（打開分頁就是新的），US2 讓使用者連分頁都不必開。

**Independent Test**: 設定一個高於當前價格的目標價，觸發重掃，確認收到
含價格與連結的通知；再觸發一次確認不重複通知。

**Acceptance Scenarios**:

1. **Given** 目標價 NT$38,000 而重掃後最低四段票價為 NT$37,265，
   **When** 掃描完成，**Then** 使用者收到 Telegram 通知，內容含條件名稱、
   價格、主行程日期、外站與查價連結。
2. **Given** 上述通知已送出，**When** 下一次重掃價格仍低於目標價且**沒有
   更低**，**Then** 不重複通知。
3. **Given** 已通知過，**When** 後續重掃出現**比上次通知時更低**的價格，
   **Then** 再次通知（值得再看一眼）。
4. **Given** 四段票價 NT$37,500、接駁估價 NT$6,000（總成本 NT$43,500）、
   目標價 NT$38,000，**When** 判定是否達標，**Then** **觸發通知**——
   達標判定只看四段票價，不含接駁估價。
5. **Given** 條件未設定目標價，**When** 重掃完成，**Then** 不發送任何通知。
6. **Given** Telegram 未設定或發送失敗，**When** 嘗試通知，
   **Then** 掃描結果照常保存，介面標示通知未送達，且**不因此中斷或重試掃描**。

### User Story 3 - 不因過期資料收到誤導的通知 (Priority: P3)

如果自動重掃連續失敗（外部服務長期阻擋、網站改版），系統手上的價格會
逐漸過時。此時不但要在介面標示，更重要的是**不能拿過期價格去觸發通知**——
使用者收到「降價了」跑去看卻發現是舊資料，比沒收到通知更糟。

**Why this priority**: 屬於正確性保護而非新價值。US1/US2 在一切正常時
已完整可用；這一項處理的是持續失敗的情境。

**Independent Test**: 讓某條件連續兩個重掃週期都失敗，確認狀態標為過期，
且即使其舊價格低於目標價也不發送通知。

**Acceptance Scenarios**:

1. **Given** 某條件連續兩個重掃週期未成功更新，**When** 檢視分頁，
   **Then** 該條件標示為資料可能已過期，並顯示上次成功時間。
2. **Given** 條件處於過期狀態且其舊價格低於目標價，**When** 判定是否通知，
   **Then** **不發送通知**。
3. **Given** 過期條件的下一次重掃成功，**When** 完成，
   **Then** 過期標示解除；若此時價格達標則正常通知。
4. **Given** 某次重掃只完成部分組合（配額不足或被阻擋），**When** 判定
   是否算成功一輪，**Then** **不更新上次成功時間**——否則過期判定會被
   部分完成的掃描一直往後推，讓過期價格看起來永遠是新的。

---

### Edge Cases

- 排程執行時服務未啟動 → 排程本身是獨立腳本，不依賴網頁服務在跑
- 同一條件的排程與使用者手動觸發同時發生 → 不重複執行，以既有進度回應
- 條件在排程到期前被刪除 → 排程跳過該條件，不報錯
- 所有條件都沒設定目標價 → 重掃照常，只是不會有任何通知
- Telegram 設定檔不存在 → 視為未設定，跳過通知並記錄，不影響掃描
- 通知送出後使用者調低目標價使其不再達標 → 不撤回已送出的通知
- 重掃當下配額為 0 → 該次排程不執行查詢，留待下次
- 系統長時間關機錯過多次排程 → 開機後不補跑積欠的排程，等下一次到期

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 允許為每個查詢條件設定自動重掃頻率，預設每週一次。
- **FR-002**: 系統 MUST 依設定頻率自動執行重掃，無需使用者操作。
- **FR-003**: 系統 MUST 把多個條件的重掃安排在不同日，避免同時段累積查詢量。
- **FR-004**: 自動重掃 MUST 沿用既有的掃描行為（配額裁切、逐筆落地、
  軟阻擋即停），MUST NOT 另建一套掃描邏輯。
- **FR-005**: 系統 MUST 記錄每個條件的上次成功完成時間與下次預定執行時間。
- **FR-006**: 系統 MUST 在最低四段票價 ≤ 目標價時發送通知。
- **FR-007**: 達標判定 MUST 只使用四段票價，MUST NOT 納入接駁票估價。
- **FR-008**: 通知內容 MUST 包含條件名稱、四段票價、主行程起訖日、外站，
  以及可直接開啟的查價連結。
- **FR-009**: 系統 MUST NOT 對同一條件重複通知，除非出現**比上次通知時更低**
  的價格。
- **FR-010**: 未設定目標價的條件 MUST NOT 觸發任何通知。
- **FR-011**: 通知失敗 MUST NOT 中斷或重試掃描；掃描結果 MUST 照常保存。
- **FR-012**: 系統 MUST 記錄上次通知的時間與當時的價格。
- **FR-013**: 條件連續兩個重掃週期未成功更新時，MUST 標示為資料過期。
- **FR-014**: 處於過期狀態的條件 MUST NOT 觸發通知，即使其價格低於目標價。
- **FR-015**: 部分完成的掃描 MUST NOT 更新「上次成功時間」。
- **FR-016**: 排程 MUST 能獨立於網頁服務執行（服務未啟動時仍會執行）。
- **FR-017**: 系統 MUST 在介面顯示每個條件的下次預定重掃時間與上次成功時間。
- **FR-018**: 使用者 MUST 能在介面調整重掃頻率，調整後 MUST 於下次排程生效。
- **FR-019**: 通知未送達時 MUST 在介面標示，讓使用者知道要自己去看。

### Key Entities

- **查詢條件（既有，擴充）**：新增重掃頻率、下次預定執行時間、上次通知時間、
  上次通知時的價格、上次通知是否送達。其餘欄位沿用 005 已建立的。
- **排程執行紀錄**：每次自動重掃的執行時間、涵蓋的條件、結果摘要
  （成功／部分完成／失敗）、是否觸發通知。供人工排查用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者建立條件並設定頻率後，不需再手動觸發即可看到價格更新。
- **SC-002**: 多個條件的自動重掃不會在同一天累積超過速率上限的查詢量。
- **SC-003**: 價格跌破目標價後，使用者在下一次排程執行後收到通知。
- **SC-004**: 同一價格水準不會產生重複通知。
- **SC-005**: 處於過期狀態的條件產生的通知數為 0。
- **SC-006**: 通知管道失效時，掃描結果的保存率仍為 100%。

## Assumptions

- **沿用 005 的掃描能力**：本功能不重新實作查詢條件、組合枚舉、查價、
  配額守衛或狀態推導，全部沿用 `005-flight-scan-page` 已完成並驗證的實作。
- **通知管道複用既有共用模組**：專案已有為此目的建立的通知模組
  （`poc/kb-mcp/notify.py`，2026-09-17 架構體檢 B4），直接複用，
  不再寫第三份 Telegram 實作。其設計鐵則是「任何失敗都不讓呼叫端崩潰」，
  與 FR-011 一致。
- **排程機制沿用既有慣例**：以 `launchd` 執行獨立腳本，比照
  `com.alphavibe.usstockscan` 等既有排程；腳本不依賴網頁服務在跑。
- **通知對象為單一使用者**：收件人沿用共用設定檔中的既有白名單，
  本功能不新增收件人管理。
- **不補跑錯過的排程**：系統關機錯過的排程不累積補跑——機票價格是當下
  的快照，補跑舊排程沒有意義。
- **頻率的下限由速率上限決定**：外部查價服務的速率限制使高頻重掃不可行，
  介面提供的頻率選項需反映此限制。
