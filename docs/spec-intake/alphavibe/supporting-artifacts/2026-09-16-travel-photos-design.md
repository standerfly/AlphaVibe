## 二、相簿分頁（FR-062）設計

### 資料模型（全新設計）

- **`albums`**：`id`、`title`、`description`、`cover_photo_id`、
  `created_at`
- **`photos`**：`id`、`file_hash`（MD5，UNIQUE 去重）、`storage_path`、
  `storage_location`（`internal` / `external`）、`rating`（0-5）、
  `camera_model`、`lens`、`iso`、`shutter_speed`、`aperture`（四者皆修正
  AutoGallery 死欄位 bug，正確寫入）、`photo_date`、`file_size`、
  `thumbnail_path`、`imported_at`
- **`photo_albums`**：`photo_id`、`album_id`（多對多 junction，一張照片
  可屬於多個相簿）
- **`tags`**：`id`、`name`（正規化標籤主檔，不採 AutoGallery 自由文字
  塞窄表的做法，避免「紅葉」「楓葉」同義詞各自長成一個標籤）
- **`photo_tags`**：`photo_id`、`tag_id`（多對多 junction）
- **`trip_albums`**：`trip_slug`（對應 `mytravel/trips/` 資料夾名稱，
  邏輯鍵非外鍵約束，比照 `us_stock_store.py`「以 ticker 為邏輯關聯鍵、
  不建外鍵」慣例）、`album_id`（多對多，供 FR-063 旅遊分頁引用）

### 架構

獨立 `PhotoStore` 類別＋獨立 `poc/data/photos.db`，比照
`us_stock_store.py`「完全獨立、`__init__` 不掛副作用種子寫入」慣例
（AlphaVibe CLAUDE.md 2026-08-22 教訓紀錄：`KBStore.__init__` 曾無條件
呼叫種子寫入方法，導致正式資產表被污染兩次；`PhotoStore` 從設計上避免
重蹈覆轍）。

### 匯入流程

1. PO 到「相簿」分頁點「匯入照片」
2. 網頁上選本機資料夾路徑（比照 AutoGallery 的網頁式選資料夾瀏覽器，
   因 STND 跑在 Mac mini 本機、原始檔可能是大體積 RAW，不適合走 HTTP
   多檔上傳；**已知限制**：僅能在本機操作，手機/遠端瀏覽器無法選本機
   路徑，MVP 不做瀏覽器檔案上傳輔助管道）
3. 選儲存位置：內接／外接（本次手動選，MVP 不做自動冷熱分層）
4. 系統掃描來源資料夾，逐一算 MD5 hash 比對既有照片 → 顯示預覽
   「即將匯入 N 張、跳過 M 張重複」
5. PO 確認後轉**背景任務**（不同步阻塞 HTTP request）：複製檔案到目標
   儲存位置＋產生縮圖＋解析 EXIF 寫入 db
6. 完成後新照片狀態：未歸類任何相簿、無標籤、rating=0

### 整理（分類／標籤）流程

- 匯入完成的一批照片可批次多選→一次指派到某相簿（新建或既有）
- 逐張／多選→加標籤（輸入時自動帶出既有標籤清單，避免同義詞氾濫）、
  評分（0-5 星）
- 相簿管理：新建（標題＋描述）、從相簿頁「加入照片」跳出選擇器、或從
  照片列表多選後「加入相簿」、設封面照、改名／刪除相簿

### 瀏覽流程

相簿列表（卡片：封面＋標題＋張數）→ 點入相簿看縮圖牆（可依日期/評分
排序、可用標籤篩選）→ 點單張看詳情（大圖、EXIF、所屬相簿、標籤、可調
rating）。

### 儲存策略

- 原始檔：內接或外接硬碟，匯入當下手動選
- 縮圖＋`photos.db`：固定存內接（跟 STND 其他資料同位置），縮圖瀏覽不
  依賴外接硬碟是否掛載
- 外接硬碟未掛載：縮圖牆與 metadata 正常瀏覽，「檢視原圖／下載」按鈕
  顯示「原檔離線」並停用，不視為錯誤狀態

### 刪除行為

僅刪除資料庫紀錄（從相簿/標籤/瀏覽列表移除），**不**刪除磁碟上的原始
檔案——檔案刪除不可逆，MVP 階段先求安全；真要清磁碟空間，之後可做一個
獨立的「清理未歸類照片」功能，跟一般瀏覽/整理操作分開，降低誤刪風險。

### Deferred（後期規劃，非本輪 MVP 承諾範圍）

- RAW／Sigma dp X3F 轉 JPG 的混合處理流程（原規劃引用開源 x3f_tools＋
  Sigma Photo Pro 官方軟體人工轉出正式版；Sigma Photo Pro 經查證無法被
  腳本自動化，即使實作仍需人工介入監看資料夾流程）
- 自動冷熱儲存分層（依存取頻率/時間自動搬移原始檔位置）
- 瀏覽器檔案上傳（供行動裝置/遠端補充少量照片用）

## 三、旅遊分頁（FR-063）設計

### 定位

**唯讀展示層**，呈現獨立專案 `/Users/stander/My_project/mytravel/` 既有
的行程手記，不搬移、不重寫原始 markdown 檔案，不改變 PO 現有「用聊天與
Claude 共創行程」的寫作習慣。

### mytravel 現況查證摘要

- `mytravel/` 是純個人筆記空間，明文不套用本 repo 的專案接入制度（見
  該資料夾 README）
- `trips/` 下每個子資料夾代表一趟旅行，命名慣例 `YYYY-MM-目的地`
  （例：`2026-10-奧日光奧會津`），內含一份 `itinerary.md`，複製自
  `templates/trip-template.md`
- 內容是高密度敘事型 markdown：每日行程表、攝影/車宿卡位指南、採購/
  咖啡豆地圖、車上料理筆記、預算追蹤、心得檢討；查證的實際範例
  （2026-10 奧日光奧會津）達 256 行，含大量彈性備案與不確定性註記
  （例：「⚠️ 未直接查證，建議行前再確認」）
- **目前完全沒有任何照片連結機制**，純文字＋表格

### Trip 列表／詳情頁

- **Trip 列表頁**：STND 後端自動掃描 `mytravel/trips/` 資料夾，用資料夾
  名稱解析標題與大致日期，卡片式列出（標題、日期範圍、封面照——來源為
  對應相簿的第一張照片，若無連結相簿則無封面）；不需要 PO 手動註冊新
  行程，複製 template 開始寫就會自動出現
- **Trip 詳情頁**：把 `itinerary.md` 原文渲染成網頁（markdown→HTML），
  保留原始敘事結構，同時嵌入該趟旅行對應相簿（透過 `trip_albums`）的
  照片縮圖牆

### Trip↔Album 關聯

多對多（見上方 `trip_albums`），可在 Trip 詳情頁或相簿頁任一端手動
設定連結；一趟旅行可連結 0 或多個相簿，一個相簿也可被多趟旅行引用
（例如橫跨多趟旅行的主題相簿），也支援未來非旅遊的相簿獨立存在。

### 明確排除

- 不做行程內容的結構化編輯表單（不拆解成 `itinerary_items`／`expenses`
  等獨立資料表）——理由：現有 markdown 格式承載大量彈性備案與不確定性
  註記的敘事風格，強制塞入固定表單欄位會損失這個優點且開發量大增
- 不對 mytravel 原始檔案做任何寫入/修改（純唯讀）
- 不做行程搜尋／跨行程比對等進階功能

### 與相簿分頁的依賴關係

本功能的照片顯示依賴相簿分頁（FR-062）已上線，開發順序建議相簿基礎版
先行，再做旅遊唯讀 viewer。

## 四、2026-09-17 補充：全域搜尋與標籤／評分中繼資料同步

來源：PO 提出「核心需求」——能用相機型號、鏡頭型號、日出/夕陽/夜景/
街拍/京都這類描述快速搜出照片，資訊要能快速加入、跟著相片、能被快速
搜尋與瀏覽。對應決策：clarification-log.md Q-050；product-spec.md
FR-062 相應章節。

### 為什麼這是「核心」而不是次要的整理功能

昨天（2026-09-16）的設計把標籤/評分放在「照片整理」底下，當作相簿內
瀏覽時的輔助篩選。PO 今天明確定調：**搜尋是這個分頁存在的主要理由**，
不是找到照片後順手篩一下。這改變了兩件事：(1) 搜尋入口要是跨相簿的
全域功能，不能只是某個相簿詳情頁裡的 filter tabs；(2) 加標籤這個動作
的效率（快速加入）跟持久性（跟著相片走）本身就是要被特別設計的功能，
不是「順便有」。

### 全域搜尋設計

- 搜尋入口獨立於相簿列表/相簿詳情頁，橫跨所有相簿
- 可組合查詢維度：
  - **結構化 EXIF**：`camera_model`、`lens`（`photos` 表既有欄位，
    UI 呈現為下拉選單，選項來自資料庫既有值，不是自由輸入）
  - **標籤**：多選，一般標籤不特別分類——場景描述（日出、夕陽、夜景、
    街拍…）、地點（京都…）都是同一個 `tags` 表裡的普通標籤，PO 想
    怎麼標都可以，不強制分類體系
- 搜尋結果以縮圖牆呈現（跟相簿內瀏覽同一套元件），可再點入單張詳情
- **搜尋只讀資料庫**（`photos`／`tags`／`photo_tags` 的 join/query），
  不讀檔案中繼資料——資料庫是唯一的搜尋來源，這樣搜尋速度快、且不受
  外接硬碟是否掛載影響（縮圖與所有可搜尋欄位都在內接硬碟上的 db）

### 快速加入資訊（標記效率）

- 加標籤時輸入自動帶出既有標籤清單（2026-09-16 已定案，避免同義詞
  氾濫）
- **新增**：常用標籤提供快速按鈕（例如日出/夕陽/夜景/街拍這類 PO
  高頻使用的詞），瀏覽單張或批次多選時一鍵套用，不用每次都打字
- 批次指派相簿／標籤／評分（2026-09-16 已定案）維持不變，是「快速
  加入資訊」的另一半（一次處理一批，不用逐張點）

### 標籤／評分「跟著相片走」＝寫回檔案中繼資料

PO 選擇的方向：標籤（keywords）與評分（rating）除了存在 STND 資料庫，
還要**寫進照片檔案本身的 XMP/IPTC 中繼資料**，這樣即使照片被複製到
STND 以外（Lightroom、Finder、傳給別人），這些資訊仍然可見——不希望
被 STND 這個工具鎖住。相簿歸屬與 trip 關聯是 STND 專屬的組織性概念，
XMP/IPTC 沒有對應的標準欄位，因此**維持只存資料庫，不寫入檔案**。

**架構原則：資料庫是唯一真相來源，檔案中繼資料只是單向鏡射（db →
檔案），STND 從不反過來讀檔案中繼資料做搜尋或還原資料。** 這個方向性
很重要：檔案中繼資料的角色是「離開 STND 之後的可攜性」，不是「另一份
可信資料來源」——如果將來哪個工具改壞了檔案的 XMP，STND 的資料庫不受
影響，PO 的搜尋與瀏覽體驗也不受影響。

**新增依賴**：`exiftool`（系統層外部工具，非 Python 套件），經
Homebrew 安裝於 Mac mini。選它的理由：業界標準、支援格式廣、對 JPG
的 XMP/IPTC 讀寫穩定；`app/requirements.txt` 目前僅有 fastapi/uvicorn
兩個 Python 套件，`exiftool` 是套件之外的系統層安裝，需要在部署文件
另外記錄安裝步驟（`brew install exiftool`）。

**執行方式**（避免同步寫檔卡住畫面，沿用匯入流程的背景任務模式）：

1. PO 在照片詳情頁或批次操作中變更標籤/評分
2. 立即寫入 `photos.db`（`photo_tags`／`photos.rating`）——畫面與
   全域搜尋馬上反映這個變更
3. 轉背景任務呼叫 `exiftool`，把該照片目前完整的標籤清單與評分寫入
   檔案的 XMP/IPTC 欄位
4. 寫入成功 → `photos.metadata_sync_status = 'synced'`，記錄
   `metadata_synced_at`
5. 寫入失敗或原始檔所在硬碟未掛載 → 標記 `pending`（硬碟離線，可能
   之後就通）或 `failed`（exiftool 回報錯誤，如檔案損壞、格式不支援、
   權限問題），錯誤原因記在 `metadata_sync_error`；**不阻擋** db 端的
   標籤/評分/搜尋照常使用

**離線/失敗的復原方式（MVP 故意簡化）**：不做自動偵測「外接硬碟重新
掛載」事件（會需要額外的檔案系統監看機制，MVP 階段不做）；改用照片
詳情頁一個「重新同步」按鈕，PO 確認硬碟已接上後手動點擊補寫。這跟
2026-09-16 定案的「匯入時手動選儲存位置、不做自動冷熱分層」是同一個
MVP 簡化原則的延伸：能用手動操作解決的，先不做自動偵測。

**資料模型新增欄位**（`photos` 表）：`metadata_sync_status`
（`synced` / `pending` / `failed`）、`metadata_synced_at`（時間戳，
nullable）、`metadata_sync_error`（文字，nullable，記錄失敗原因）。

### 關鍵技術決策：`file_hash` 匯入後永久不重算

這是這輪討論浮現的一個容易被忽略、但會直接破壞去重機制的細節：

- `file_hash`（MD5）原本的用途是匯入時的去重比對鍵
- 中繼資料寫回會改變檔案本身的位元組（XMP/IPTC 是寫進檔案內的）
- 如果之後又對同一張照片重新計算 hash，會得到跟匯入當下不同的值
- **決策**：`file_hash` 只在匯入當下對原始位元組算一次，永久保存，
  **之後任何時候都不重新計算**——即使我們自己的中繼資料寫回改變了
  檔案內容。這樣「同一份原始素材（PO 電腦裡還沒被 STND 動過的那份
  來源檔）」之後再匯入一次時，算出來的 hash 仍然對得上資料庫裡存的
  舊值，正確判定為重複而跳過
- 這是刻意的設計，未來接手開發或維護的人**不要「修正」成即時重算
  hash**，那樣會讓去重機制整個失效

### 範圍與 Deferred

- MVP 僅處理 JPG 的中繼資料寫回（沿用 FR-062 主範圍：RAW/X3F 轉檔
  本身就是 Deferred）
- RAW／X3F 檔案的中繼資料寫回方式列入 Deferred，待 RAW pipeline 開發
  時一併研究——直接改 RAW 檔案的二進位有風險（可能不被相機軟體正確
  識別、甚至損毀原始檔），屆時可能需要改用 XMP sidecar 檔（同名
  `.xmp` 檔案，跟原始檔放在一起，不動 RAW 本身）而不是直接寫入
- 自動偵測外接硬碟重新掛載事件列入 Deferred（MVP 用手動「重新同步」
  按鈕）
