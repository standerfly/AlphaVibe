## User Scenarios & Testing *(mandatory)*

### User Story 1 - 交易紀錄匯入與股價走勢對照 (Priority: P1)

使用者上傳一張券商 App 的交易截圖，系統辨識出交易明細，使用者在核對畫面
確認或修正後匯入，該筆交易隨即出現在對應個股的股價走勢圖上，與買賣點位
一併呈現。

**Why this priority**：這是整個系統的基礎——沒有交易紀錄與股價對照，後續的
研究筆記、關注條件都沒有「持股現況」可以依附。這個故事本身就能獨立交付
價值：使用者能把原本散落在券商 App 截圖裡的交易，變成一張看得懂進出場
時機的圖表。

**Independent Test**：上傳一張測試截圖 → 核對辨識結果 → 確認匯入 → 打開
該股個股詳情頁，能看到股價線＋對應的買賣點位標記，即完成獨立驗證。

**Acceptance Scenarios**：

1. **Given** 使用者在美股分頁的交易匯入畫面，**When** 上傳一張清晰的券商
   截圖，**Then** 系統顯示辨識出的日期/代號/買賣方向/股數/價格核對表
2. **Given** 核對表已顯示辨識結果（可能不完整），**When** 使用者手動修正/
   補齊欄位後點擊確認匯入，**Then** 該筆交易寫入美股獨立交易紀錄，且該股
   若尚未在追蹤清單中會自動出現
3. **Given** 使用者已匯入至少一筆某股票的交易，**When** 使用者打開該股個股
   詳情頁，**Then** 顯示股價走勢圖，圖上以買=紅點、賣=綠點標記對應交易
   （沿用台股既有紅漲綠跌配色慣例）
4. **Given** 使用者在核對畫面尚未確認，**When** 使用者取消匯入，**Then**
   暫存的截圖與未確認資料一併捨棄，不留下任何紀錄

---

### User Story 2 - 研究筆記與投資立場記錄 (Priority: P2)

使用者與 agent 討論一檔美股的後勢後，把討論結果（結構化立場＋完整論述）
存入系統，之後在個股詳情頁可以隨時查看完整的研究筆記內容，不需要重新
翻找對話紀錄。

**Why this priority**：在 P1 建立的「看得到持股」基礎上，這個故事解決
「當初為什麼買/為什麼還抱著」容易遺忘的問題，是把系統從「記帳工具」
升級成「投資決策紀錄」的關鍵一步，但即使沒有 P1 的匯入功能，使用者
也能單獨對一檔還沒交易、純觀察中的股票建立研究筆記（見 Edge Cases）。

**Independent Test**：與 agent 針對一檔股票討論後勢 → 確認存入結構化
立場與研究筆記 → 打開個股詳情頁的「投資立場」卡片 → 能看到立場摘要，
點擊可查看完整研究筆記（章節、引用來源、情境價格帶皆完整呈現），
即完成獨立驗證。

**Acceptance Scenarios**：

1. **Given** 使用者與 agent 討論完一檔股票，**When** 確認將討論結果存入
   系統，**Then** 系統存入結構化立場（買/賣/觀望＋Bear/Base/Bull 情境
   價格帶＋論點摘要）與完整研究筆記內容
2. **Given** 某股票已有研究筆記，**When** 使用者打開該股個股詳情頁，
   **Then** 「投資立場」卡片顯示立場摘要，且提供連結可查看完整研究筆記
3. **Given** 使用者點擊查看完整研究筆記，**When** 頁面渲染研究筆記內容，
   **Then** 全部章節、引用來源、情境價格帶都完整呈現，不因版面密度而被
   省略或壓縮

---

### User Story 3 - 關注條件監控與觸發推播 (Priority: P3)

使用者為追蹤中的股票設定監控門檻（例如股價、毛利率等指標），系統每天透過
背景排程查詢最新資料並比對，一旦碰觸門檻就在頁面上標示警示狀態，並透過
既有 Telegram 閘道主動推播通知。

**Why this priority**：這是系統從「被動記錄」進化到「主動提醒」的最後一塊
拼圖，依賴 P1（有股票可以監控）與 P2（知道當初設定的門檻是什麼）已經建立
的基礎資料，但監控條件本身的設定與觸發判斷可以獨立測試，不需要等前兩個
故事的每個細節都完工。

**Independent Test**：為一檔股票設定一個容易觸發的門檻（例如「股價高於
目前價格的一半」）→ 等待或手動觸發當日排程執行 → 確認美股 landing 頁與
個股詳情頁都顯示「已觸發」狀態、且收到 Telegram 推播，即完成獨立驗證。

**Acceptance Scenarios**：

1. **Given** 使用者為某股票設定一個監控門檻，**When** 當日排程刷新查詢到
   的最新資料碰觸該門檻，**Then** 該股在美股 landing 頁與個股詳情頁都
   標示為「已觸發」狀態，且透過 Telegram 閘道推播通知
2. **Given** 某股票的監控門檻尚未被碰觸，**When** 使用者查看美股分頁，
   **Then** 該股顯示「未觸發」狀態（不與「已觸發」混淆）
3. **Given** 該股票從未成功取得過資料（例如剛加入追蹤、或代號查無此股），
   **When** 系統嘗試比對監控門檻，**Then** 顯示「資料不足」狀態，不誤判
   為「未觸發」，也不觸發推播
4. **Given** 該股票當日排程因外部資料源額度用盡而被跳過，**When** 使用者
   查看美股分頁，**Then** 顯示「未更新（無額度）」，監控條件維持上一次
   成功評估的狀態，不因跳過而改判為「資料不足」或觸發新的推播
5. **Given** Telegram 閘道當下無法送出推播，**When** 監控門檻仍然被碰觸，
   **Then** 美股分頁的警示狀態仍正常標示，不因推播失敗而遺漏警示

---

### Edge Cases

- 截圖完全無法辨識出任何交易明細（例如截圖模糊、上傳了非交易紀錄畫面）：
  核對畫面呈現全空白欄位，由使用者手動輸入全部欄位；不會因為辨識失敗
  就拒絕整個匯入流程
- 使用者針對一檔從未交易過、純粹想觀察的股票直接建立研究筆記或監控條件
  （不透過 User Story 1 的交易匯入）：系統允許，該股同樣會出現在美股
  landing 的追蹤清單中（追蹤狀態不要求必須先有交易紀錄）
- 使用者輸入的股票代號查無此股（拼字錯誤或代號不存在）：系統提示查無
  此股票，不建立追蹤項目
- 使用者對同一張截圖重複執行匯入流程兩次：系統不做自動去重判斷，由
  使用者在核對畫面自行辨識是否為重複交易並決定是否確認
- 監控門檻連續多天處於「已觸發」狀態：只在狀態從「未觸發/資料不足」轉為
  「已觸發」的當次排程推播通知一次，之後除非狀態先轉回未觸發、再次被
  碰觸，否則不重複推播
- 當日排程因外部資料源額度用盡而跳過部分股票：這些股票顯示「未更新
  （無額度）」，監控條件維持上一次成功評估的狀態，不視為「資料不足」，
  也不因跳過而觸發新的推播
- 使用者的 API 金鑰失效或未設定：系統顯示對應股票的報價/基本面資料為
  「資料不足」，不影響其他已有資料的股票正常顯示

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在 STND 導覽提供一個獨立的「美股」分頁入口，不與
  既有「投資」（台股）或「資產」分頁共用畫面或選單項目
- **FR-002**: 系統 MUST 支援使用者上傳交易截圖，辨識出交易明細（日期/
  代號/買賣方向/股數/價格），並在使用者確認前一律呈現可編輯的核對畫面
- **FR-003**: 系統 MUST 讓使用者在核對畫面修正或補齊任何欄位後，才能將
  交易寫入美股獨立交易紀錄；使用者取消時暫存資料與截圖一併捨棄
- **FR-004**: 系統 MUST NOT 永久保存交易截圖原始檔——截圖僅在辨識/核對
  流程中暫存，流程結束（確認或取消）後即刪除
- **FR-005**: 系統 MUST 在個股詳情頁提供股價走勢圖，並在圖上疊加使用者
  的買賣交易點位標記
- **FR-006**: 系統 MUST 每天透過背景排程（每日一次，比照既有台股
  `market_scan.py` 的排程模式），自動為所有追蹤中的股票，向外部報價
  資料源查詢最新的股價與基本面資料（毛利率、營收等）
- **FR-007**: 系統 MUST 在排程刷新時，若主要報價資料源查詢失敗或額度
  用盡，自動嘗試備援資料源；若一檔股票從未成功取得過任何資料，視為
  「資料不足」
- **FR-008**: 系統 MUST 支援使用者將與 agent 的討論結果存入結構化投資
  立場（買/賣/觀望方向＋Bear/Base/Bull 情境價格帶＋論點摘要）
- **FR-009**: 系統 MUST 在個股詳情頁完整呈現研究筆記內容（含所有章節、
  引用來源、情境價格帶），呈現時不得因版面密度考量而省略或壓縮內容
- **FR-010**: 系統 MUST 讓使用者為追蹤中的股票設定監控門檻（可設定的
  指標包含但不限於股價、毛利率等基本面數值）
- **FR-011**: 系統 MUST 在排程查詢到最新資料時，將結果與使用者設定的
  監控門檻比對，並以三種狀態呈現：未觸發／已觸發／資料不足；當日未能
  刷新到新資料的股票（見 FR-017），監控條件狀態維持上一次成功評估的
  結果，不因此改判為「資料不足」
- **FR-012**: 系統 MUST 在監控門檻的狀態由「未觸發」或「資料不足」轉為
  「已觸發」時，透過既有 Telegram 閘道推播通知使用者；同一項門檻持續
  處於已觸發狀態時不重複推播
- **FR-013**: 系統 MUST 讓使用者在美股分頁的追蹤清單一次檢視所有追蹤中
  股票的現價、漲跌、投資立場、監控觸發狀態，以及資料是否為當日排程
  已刷新（或顯示「未更新（無額度）」，見 FR-017）
- **FR-014**: 系統 MUST 在美股相關的漲跌與買賣點位視覺呈現上，沿用既有
  台股慣例（上漲/買進為紅色，下跌/賣出為綠色），與 STND 其餘頁面一致
- **FR-015**: 系統 MUST 確保美股的資料表（交易紀錄、投資立場、監控條件、
  報價歷史）與既有台股資料表完全獨立，不共用、不混合計算（幣別 USD 與
  TWD 不合併加總）
- **FR-016**: 系統 MUST 確保美股專用的資料查詢管道與既有台股查詢管道
  完全獨立，任何美股功能的查詢/寫入路徑都不觸及台股既有的資料或工具
- **FR-017**: 系統 MUST 在當日排程因外部資料源額度上限而未能刷新部分
  股票時，將這些股票標示為「未更新（無額度）」，並保留其上一次成功
  取得的資料與監控條件評估結果——「未更新（無額度）」與「資料不足」
  是兩種不同狀態，前者代表「曾經有資料、當日沒刷到」，後者代表
  「從未成功取得過資料」，不得互相誤判

### Key Entities *(include if feature involves data)*

- **美股交易紀錄**：一筆使用者的美股買賣交易，屬性包含日期、股票代號、
  買賣方向、股數、成交價格、金額（USD）；來源是使用者上傳的截圖經核對
  確認後產生，不含截圖原始檔本身
- **美股投資立場**：某股票在某個時間點的結構化投資判斷，屬性包含股票
  代號、建立日期、方向（買/賣/觀望）、情境價格帶（Bear/Base/Bull）、
  論點摘要、完整研究筆記內容、狀態（進行中/已結束）
- **監控條件**：使用者為某股票設定的一個門檻，屬性包含股票代號、指標
  類型（價格/基本面等）、比較方式、門檻數值、目前狀態（未觸發/已觸發/
  資料不足）
- **美股報價紀錄**：某股票在某個排程執行日取得的價格/基本面快照，屬性
  包含股票代號、查詢日期、收盤價、（若有）基本面數值；由每日排程刷新
  累積形成，若當日因額度用盡而跳過該股，當天不會新增紀錄，歷史可能
  有缺口（該股顯示「未更新（無額度）」，見 FR-017）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：使用者從上傳一張標準券商截圖到完成交易匯入（含核對確認），
  整個流程可在 10 分鐘內完成，不需要手動逐筆輸入交易明細
- **SC-002**：使用者在個股詳情頁單一畫面內即可看到完整研究筆記內容，
  不需要離開 STND 或另外查找對話紀錄
- **SC-003**：監控門檻被碰觸後，使用者最晚在下一次每日排程刷新完成後
  即可於美股分頁看到警示狀態，並收到對應的 Telegram 推播通知（排程頻率
  為每日一次）
- **SC-004**：使用者可以在美股 landing 頁單一畫面內，一次看完所有追蹤
  股票的警示狀態，不需要逐檔點開比對
- **SC-005**：隨機抽查美股功能的任一查詢或寫入操作，皆不涉及既有台股
  資料表或查詢工具，兩者資料完全不互相污染

## Assumptions

- 交易截圖來源是使用者自己的券商 App/網頁畫面，非任意公開網路截圖
- 使用者是系統的唯一操作者，不需要多使用者或多角色權限設計
- 股票追蹤狀態不要求必須先有交易紀錄——建立研究筆記或監控條件也能讓
  一檔股票進入追蹤清單（見 Edge Cases）
- 外部報價/基本面資料透過每日一次的背景排程自動刷新（比照本 repo 既有
  台股 `market_scan.py` 的排程模式，收盤後執行），不依賴使用者互動觸發；
  監控門檻的即時性因此是「最晚下一次排程後可見」，不是即時反應
- 排程執行的確切時刻、如何分配免費額度給多檔追蹤股票（例如依優先序或
  單純依序執行到額度用盡為止）屬於技術實作細節，將在 `/speckit.plan`
  階段決定；本規格只定義「額度用盡時的使用者可見行為」（FR-017）
- 備援報價資料源的最終選型（Alpha Vantage 或 yfinance 等）與主/備切換
  邏輯屬於技術實作細節，將在後續 `/speckit.plan` 階段決定，不影響本規格
  對「必須有備援」這項行為需求的定義
- 使用者需要自行申請外部報價資料源的個人 API 金鑰；金鑰的儲存與管理方式
  屬於技術實作細節，將在 `/speckit.plan` 階段決定
- 美股獨立查詢管道（FR-016）的具體技術方案（獨立的一組工具、或既有工具
  加上市場區隔邏輯）屬於技術實作細節，將在 `/speckit.plan` 階段決定
- 視覺呈現延續 STND 既有的設計系統（配色、字體、卡片樣式），不建立新的
  視覺語言
- 美股投資立場的「已結束」狀態由使用者手動標記（例如全部賣出後主動關閉），
  系統不自動偵測賣出交易來改變立場狀態；這是低影響的合理預設，日後如有
  需要可再議自動化
