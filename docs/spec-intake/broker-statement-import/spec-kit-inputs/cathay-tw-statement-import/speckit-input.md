# Spec Kit Input: 國泰台股日對帳單 Email 自動匯入

**Status:** Draft
**Source Product Spec:** ../../product-spec.md
**Source Scope Decision:** ../../scope-decision.md
**Spec Feature Slug:** cathay-tw-statement-import
**Handoff Order:** 1

## Feature Summary

每個有成交的交易日，國泰綜合證券會寄一封台股日對帳單 Email 到 PO 的 Gmail，附件是加密 PDF，
內含當日交易明細與完整庫存明細。本功能在 PO 的 Mac（正式環境）上定時自動讀信、開啟 PDF、
擷取資料，直接寫入 STND 的台股交易流水表與庫存，完成後以 Telegram 通知 PO。PO 不需任何
手動操作。

## Actors

- PO（Stander）：STND 唯一使用者；接收通知；驗證期與日後抽查時提供對帳單供比對。
- 國泰綜合證券：寄送日對帳單（外部系統，格式由國泰決定）。
- 自動匯入排程：正式環境的定時工作。
- Claude：驗證期與抽查時逐筆比對；協助處理通知中需人工補救的項目。

## Problem and Goal

PO 的買賣紀錄與庫存都要自己匯入，資料容易過時，導致 STND 很少被使用。國泰沒有個人 API，
Email 日對帳單是唯一可自動化的官方管道。目標：有成交的交易日，PO 不做任何操作，當晚 STND
就有當天成交與最新庫存。

## In Scope

- 自動讀取 Gmail 中國泰台股日對帳單（只認寄件人 `e-notification@ebill1.cathaysec.com.tw`
  且主旨「國泰綜合證券日對帳單」）。
- 以 PO 身分證字號（英文字母大寫）開啟加密 PDF。
- 擷取交易明細寫入台股交易流水表；擷取庫存明細更新台股庫存。
- 直接寫入、事後以 Telegram 通知。
- 處理紀錄、錯誤處理、手動重跑。
- 驗證期與日後抽查的比對方式。

## Out of Scope

- 美股（國泰複委託）對帳單——另一個輸入包，待樣本。
- 成交回報 Email、月對帳單、其他券商。
- 下單或任何改變券商帳戶的動作；自動登入國泰網頁。
- 訂閱生效（2026-10-29）前的歷史回補。

## User Scenarios

1. PO 某交易日買進 1 檔，當晚對帳單寄達；下一次排程處理後，STND 有該筆成交（代號正確）與
   對帳單的庫存，PO 收到 Telegram 成功摘要。
2. 同日多筆買賣（含賣出、零股）全部正確寫入。
3. 同一份對帳單處理兩次，沒有重複成交。
4. 某筆成交先前已用 CSV 手動匯入，對帳單處理時該筆被跳過。
5. 某筆成交名稱對不到代號：其餘照常寫入，通知列出該筆。
6. PDF 打不開或格式無法辨識：不寫入任何資料，通知錯誤原因；修正後手動重跑成功。
7. 對帳單庫存與買賣紀錄推算不一致（例如配股）：庫存以對帳單寫入，通知列出差異。
8. 某晚沒收到信，之後收到時仍會被處理。
9. 驗證期：PO 提供手動申請的對帳單，與資料庫逐筆比對；連續 3 次一致即結束驗證期。

## Functional Requirements

- FR-001 定時檢查 Gmail，取得尚未處理的國泰台股日對帳單；其他信件一律忽略；當晚沒收到的
  之後要能補處理，不遺漏。
- FR-002 以身分證字號（英文字母大寫）開啟加密 PDF。
- FR-003 交易明細每筆成交寫入台股交易流水表：成交日、代號、買賣別、股數、單價；手續費與
  交易稅一併保留。
- FR-004 交易明細只有股票名稱：先對照同份對帳單的庫存明細，再用既有名稱→代號解析；都對不到
  的成交不寫入、列入通知。
- FR-005 同一筆成交（委託書號相同）只寫入一次，含已用交易明細表或 CSV 手動匯入過的成交；
  同一份對帳單處理多次，結果與處理一次相同。
- FR-006 對帳單是標準：以庫存明細（完整持股）更新該日庫存，未列出的股票視為已無持股。平均
  成本沿用 STND 既有成本；新出現的股票用買賣紀錄推算，算不出來留空並在通知標示。
- FR-007 比對「買賣紀錄推算的庫存」與「對帳單庫存」；不一致時仍以對帳單寫入，差異列入通知。
- FR-008 寫入前不需 PO 確認。每份對帳單處理完以 Telegram 傳摘要：對帳單日期、寫入成交筆數、
  庫存檔數、差異或錯誤；處理失敗一定通知；沒有新對帳單時不通知。
- FR-009 PDF 打不開或格式無法辨識時，整份不寫入任何資料（全有或全無），並通知 PO。
- FR-010 保存每份對帳單的處理紀錄（日期、狀態、寫入筆數、差異、錯誤）；自動匯入的資料可與
  手動匯入區分。
- FR-011 驗證期：PO 手動申請的對帳單與資料庫逐筆比對，連續 3 次全部一致即結束，任一次不
  一致則修正後重新起算；之後 PO 不定期請 Claude 抽查。
- FR-012 Gmail 應用程式密碼與身分證字號只存在 PO 的 Mac 鑰匙圈，不得出現在 repo、設定檔、
  對話或通知；對帳單上的個資（姓名、帳號、地址）不寫入資料庫。

## Success Criteria

- 有成交的交易日，PO 不做任何操作，對帳單寄達後的下一次排程內 STND 已有當天成交與庫存。
- 驗證期連續 3 次比對，寫入的成交與庫存與國泰對帳單逐筆一致。
- 上線後交易流水表沒有重複成交。
- 每次處理失敗，PO 都收到通知。

## Constraints and Assumptions

- 國泰無個人 API；對帳單格式由國泰決定，可能改版（改版時以「格式無法辨識」處理，不猜測）。
- 對帳單於交易日約 18:30 起寄送（樣本 19:12 寄達）。
- 正式環境在 PO 的 Mac 上（獨立 worktree `AlphaVibe-prod`，macOS launchd 排程）；Mac 睡眠時
  排程延後到喚醒；既有每日健康檢查應涵蓋本排程。
- 假設：沒有成交的交易日國泰不寄日對帳單（待觀察）。
- 假設：庫存明細已含當日未交割的成交（樣本顯示如此，待驗證期確認）。
- 本功能是 STND「未經確認不寫入」規則的明確例外；其他匯入管道仍需事前確認。
- 既有能力可沿用：國泰交易明細表的類別判讀（「集買」等）、委託書號防重複、名稱→代號解析、
  買賣紀錄同步庫存、Telegram 通知模組。
- 對帳單欄位結構見 product-spec 來源 SRC-002（交割金額、交易明細、庫存明細三區塊）。

## Source Decisions

- Q-001：直接寫入、事後通知（例外於「未經確認不寫入」）。
- Q-002：對帳單是標準；成本沿用既有。
- Q-003：Telegram 摘要通知。
- Q-004：敏感資料只存 Mac 鑰匙圈；只讀國泰對帳單。
- Q-005：驗證期連續 3 次比對一致；之後不定期抽查。
- Q-008：不回補歷史。
