# Feature Specification: 機票掃描分頁

**Feature Branch**: `005-flight-scan-page`
**Created**: 2026-09-23
**Status**: Draft
**Input**: `docs/spec-intake/flight-search/spec-kit-inputs/flight-scan-page/speckit-input.md`（Accepted）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 不指定日期就看到便宜組合 (Priority: P1)

使用者想去某個目的地，只知道「大概什麼季節、行程幾天」，不想自己逐一試日期。
他在分頁上建立一個查詢條件（目的地、候選外站、出發區間、行程天數），
系統在該區間內抽樣日期並查價，回傳依價格排序的「日期＋外站」組合。
使用者看完後自行判斷哪個時段請假可行。

**Why this priority**: 這是整個功能存在的理由。使用者的原話是「日期才是我最困擾的，
我想要的是你找到便宜的機票，然後我再看時間是否適合」。沒有這一項，其餘功能
都沒有意義；有了這一項，即使沒有其他功能也已可用。

**Independent Test**: 建立一個條件、觸發掃描、確認得到依價格排序的結果清單，
且全程未輸入任何具體出發日。可完全獨立驗證並交付價值。

**Acceptance Scenarios**:

1. **Given** 使用者未建立任何查詢條件，**When** 他填入目的地、兩個候選外站、
   出發區間 2027-04～2027-06、行程 12 天並送出，**Then** 系統建立該條件，
   且條件在重新開啟分頁後仍存在。
2. **Given** 已建立的查詢條件，**When** 使用者觸發掃描並等待完成，
   **Then** 系統顯示依價格排序的組合清單，每筆含主行程起訖日、外站、
   四段票價（NTD）、航空公司、第1段日期。
3. **Given** 使用者全程未輸入任何具體出發日，**When** 掃描完成，
   **Then** 結果中的出發日由系統在區間內抽樣產生。
4. **Given** 某個日期組合先前已查過，**When** 再次掃描同一條件，
   **Then** 該組合不重複向外部查價。
5. **Given** 掃描已完成，**When** 使用者重新開啟分頁，
   **Then** 立即看到既有結果，不需等待重新掃描。
6. **Given** 某個組合查價成功但無任何可用票價，**When** 顯示結果，
   **Then** 該筆標示為「查無票價」，與「查詢失敗」明確區分。

### User Story 2 - 設定兩端間隔以分散行程 (Priority: P2)

四段票的第1段（外站→樞紐）與第4段（樞紐→外站）可以離主行程很遠。
使用者想把它們拉開，讓第1段成為另一趟獨立旅行的回程、第4段成為再一趟的去程，
避免在短期內密集請假。他為兩端各自選擇間隔策略，並可指定不希望航段落入的月份。

**Why this priority**: 這是使用者第二個明確痛點（原話「這樣我才不用密集請假」），
且第4段的日期同時是重要的價格槓桿——實測同樣四個班機、僅第4段差 12 天，
票價相差 21.9%。但 US1 在使用預設間隔的情況下已可運作，故列 P2。

**Independent Test**: 對同一組主行程，分別選「不拉遠」與「約 3 個月」兩種策略，
確認第1段與第4段的日期隨之改變且互不影響。可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 一個查詢條件，**When** 使用者將第1段策略設為「約 5 個月」、
   第4段設為「約 3 個月」，**Then** 結果中第1段約在主行程前 150 天、
   第4段約在回程後 90 天。
2. **Given** 使用者為兩端設定不同策略，**When** 掃描完成，
   **Then** 兩端的間隔互不影響（可一端拉遠、另一端不拉遠）。
3. **Given** 使用者複選排除月份 6、7、8，**When** 選擇「自動避開排除月份」策略，
   **Then** 主行程、第1段、第4段的日期皆不落在該三個月份。
4. **Given** 使用者改為複選 12、1、2（南半球旺季），**When** 掃描完成，
   **Then** 行為與情境 3 一致，系統不因月份組合不同而失效。
5. **Given** 使用者複選不連續月份 2、7、12，**When** 掃描完成，
   **Then** 三個航段皆不落在這三個月份。
6. **Given** 使用者選擇第4段「約 3 個月」，而回程後 1 天所在月份未被排除，
   **When** 系統挑選間隔，**Then** 系統回傳接近 90 天的值，
   **不得**因「回程後 1 天剛好合格」而挑到緊接回程的值。
7. **Given** 某個主行程日期在所有候選間隔下都無法避開排除月份，
   **When** 掃描執行，**Then** 該日期整組被跳過，且介面說明跳過原因。

### User Story 3 - 大範圍掃描不因外部限制而失敗 (Priority: P3)

使用者想一次掃很多組合（多個外站 × 多個日期）。但外部查價服務有速率限制，
超量會被暫時阻擋。系統必須自動把掃描量控制在安全範圍、把其餘排隊，
並在被阻擋時停止而非持續重試，同時保留已完成的部分。

**Why this priority**: 沒有這一項，小範圍掃描仍可用（US1、US2 成立）；
但一旦使用者勾選多個外站，掃描就會中途失效且可能丟失已完成結果。
這是可靠性而非核心價值，故列 P3。

**Independent Test**: 建立一個超過單時段配額的條件，確認系統完成可執行量、
顯示剩餘筆數與預估接續時間、且下個時段自動續掃未完成者。可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 一個條件含 24 個組合而本時段僅剩 20 次配額，**When** 觸發掃描，
   **Then** 系統查完 20 筆、顯示「已完成 20／24」與預估接續時間，不回報錯誤。
2. **Given** 上述掃描已完成 20 筆，**When** 配額釋出後再次執行，
   **Then** 系統只查剩餘 4 筆，不重查已完成者。
3. **Given** 掃描進行中連續 3 筆查價逾時，**When** 系統偵測到此情況，
   **Then** 立即停止本批、保留已完成結果、顯示「偵測到連續逾時」與建議等待時間，
   且不再發出請求。
4. **Given** 掃描進行到第 8 筆時服務被重新啟動，**When** 使用者再次觸發，
   **Then** 前 8 筆的結果仍存在，系統只查第 9 筆之後的組合。
5. **Given** 單一組合查價逾時（非連續），**When** 系統處理，
   **Then** 重試一次；若前一筆已失敗則不重試。
6. **Given** 使用者開啟分頁，**When** 檢視配額資訊，
   **Then** 看到滾動時間窗內的已用量與剩餘量，且介面標明該限制值是實測值或推估值。

### User Story 4 - 核對價格並避開票規風險 (Priority: P4)

使用者不會只看系統給的數字就下單。他要能一鍵開啟外部頁面核對實際航班與價格，
也要知道這種票的關鍵風險（第1段不可缺搭、僅經濟艙適用），
以及台北→外站的接駁票要另外自費。

**Why this priority**: 不影響掃描本身的運作，但缺少它使用者無法安心行動，
且可能誤觸票規而讓整張票失效。屬於讓結果「可用於決策」的最後一哩。

**Independent Test**: 從任一筆結果點開外部連結，確認開啟的行程與該筆一致；
確認風險提示與接駁票估價可見。可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 一筆掃描結果，**When** 使用者點擊四段票查價連結，
   **Then** 外部頁面顯示的四個航段與日期與該筆結果一致。
2. **Given** 一筆掃描結果，**When** 使用者點擊接駁票連結，
   **Then** 外部頁面顯示樞紐→外站的單程查詢，日期對應第1段出發日之前。
3. **Given** 任一筆結果，**When** 顯示於清單，
   **Then** 同時顯示接駁票估價並標明為「估算值」。
4. **Given** 使用者檢視結果頁，**When** 頁面載入，
   **Then** 可見「第1段不可缺搭，否則後三段全部失效」與「僅經濟艙適用」的提示。
5. **Given** 使用者想使用外部服務自帶的價格追蹤功能，**When** 他開啟該說明，
   **Then** 看到「該功能不支援四段票」的說明，以及可用於主行程來回票的操作步驟與連結。
6. **Given** 使用者以行動裝置瀏覽器開啟分頁，**When** 檢視結果清單並點擊外部連結，
   **Then** 清單內容可完整閱讀（不需橫向捲動頁面本體），連結正確開啟對應行程。

---

### Edge Cases

- 出發區間內的所有月份都被排除 → 不執行掃描，明確告知無可掃描日期
- 出發區間起點早於今日 → 自動以今日加最小前置天數為起點
- 候選外站清單為空 → 拒絕建立條件並說明原因
- 行程天數為 0 或負數 → 拒絕建立條件
- 排除月份輸入超出 1–12 範圍 → 拒絕並說明有效範圍
- 第1段推算後落在今日之前 → 該候選間隔視為不可用，改試下一個
- 同一條件被連續觸發多次 → 不重複建立掃描作業，以既有進度回應
- 外部查價路徑長期失效 → 停止自動掃描並明確標示，仍保留既有結果與外部連結
- 刪除查詢條件 → 其掃描結果一併移除，但共用的查價快取保留

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 允許建立查詢條件，欄位包含目的地、候選外站（多選）、
  出發區間、行程天數、第1段間隔策略、第4段間隔策略、排除月份（主行程／第1段／
  第4段各自一組）、目標價。
- **FR-002**: 系統 MUST 持久保存查詢條件，重新開啟分頁後仍存在。
- **FR-003**: 系統 MUST 允許列出與刪除查詢條件；刪除時一併移除其掃描結果。
- **FR-004**: 系統 MUST 在出發區間內抽樣出發日，使用者 MUST NOT 需要指定具體日期。
- **FR-005**: 系統 MUST 依價格排序呈現結果，每筆含主行程起訖日、外站、
  四段票價、航空公司、第1段日期與間隔天數、第4段日期與間隔天數。
- **FR-006**: 系統 MUST 為第1段與第4段各自提供間隔策略，至少包含
  「不拉遠」、「約 1 個月」、「約 3 個月」、「約 5 個月」、「自動避開排除月份」。
- **FR-007**: 系統 MUST 為每個主行程日期各自挑選可行的間隔天數；
  單一固定值不足以同時滿足所有日期。
- **FR-008**: 系統 MUST 在滿足排除月份的候選中優先選擇較遠的間隔；
  MUST NOT 因最近的候選剛好合格而挑到緊接主行程的值。
- **FR-009**: 排除月份 MUST 支援 1–12 月任意複選（含不連續組合）；
  系統 MUST NOT 內建任何季節定義。
- **FR-010**: 系統 MUST 跳過所有候選間隔都無法避開排除月份的日期，並說明原因。
- **FR-011**: 系統 MUST 以背景方式執行掃描，使用者 MUST NOT 需停留於頁面等待。
- **FR-012**: 系統 MUST 在掃描量超過本時段可用配額時，裁切為可執行量並將其餘排隊，
  MUST NOT 回報為錯誤。
- **FR-013**: 系統 MUST 顯示掃描進度（已完成筆數／總筆數）與預估接續時間。
- **FR-014**: 系統 MUST 略過已有結果的組合，不重複向外部查價。
- **FR-015**: 系統 MUST 逐筆保存查價結果，使掃描中斷後已完成部分不遺失。
- **FR-016**: 系統 MUST 在連續查價失敗達門檻時停止本批、保留已完成結果、
  說明原因與建議等待時間，MUST NOT 繼續發出請求。
- **FR-017**: 系統 MUST 對單一非連續逾時重試一次；前一筆已失敗時 MUST NOT 重試。
- **FR-018**: 系統 MUST 顯示滾動時間窗內的配額使用量與剩餘量，
  並標明該限制值是實測值或推估值。
- **FR-019**: 系統 MUST 為每筆結果提供四段票與接駁票的外部查價連結，
  且連結開啟的行程 MUST 與該筆結果一致。
- **FR-020**: 系統 MUST 顯示接駁票估價並標明為估算值。
- **FR-021**: 系統 MUST 於結果頁提示「第1段不可缺搭，否則後三段全部失效」
  與「僅經濟艙適用」。
- **FR-022**: 系統 MUST 提供外部服務原生價格追蹤的操作說明，
  並說明該功能不支援四段票、僅適用主行程來回票。
- **FR-023**: 系統 MUST 區分「查無票價」與「查詢失敗」兩種結果狀態。
- **FR-024**: 所有金額 MUST 以新台幣（顯示為 NTD）呈現。
- **FR-025**: 系統 MUST 拒絕無效的條件輸入（空外站清單、非正行程天數、
  月份超出 1–12），並說明原因。
- **FR-026**: 系統 MUST 可在行動裝置瀏覽器上使用並檢視結果。

### Key Entities

- **查詢條件**：使用者定義的一組搜尋參數。含目的地、候選外站清單、出發區間、
  行程天數、兩端間隔策略、三組排除月份、目標價、狀態、上次成功更新時間。
- **掃描結果**：一個查詢條件下的一筆具體組合報價。含所屬條件、主行程起訖日、
  外站、四段各自日期、兩端間隔天數、四段票價、接駁票估價、航空公司、查詢時間、
  結果狀態（成功／查無票價／查詢失敗）。
- **查價快取**：以具體行程組合為鍵的價格紀錄，跨查詢條件共用，避免重複查價。
- **配額使用紀錄**：滾動時間窗內的查價次數，用於判斷本時段剩餘可用量。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者能在未輸入任何具體出發日的情況下，取得依價格排序的日期建議。
- **SC-002**: 使用者完成一次查詢條件的建立，所需輸入不超過 8 個欄位。
- **SC-003**: 已完成掃描的條件，重新開啟分頁後結果在 2 秒內可見（不觸發重新查價）。
- **SC-004**: 系統回報的票價與使用者在外部頁面人工核對的價格一致
  （抽驗至少 2 組，差異為 0）。
- **SC-005**: 掃描因配額或外部阻擋而中斷時，已完成結果的保留率為 100%。
- **SC-006**: 使用者可取得第1段與主行程間隔達 3 個月以上的可行組合。
- **SC-007**: 排除月份設定生效率 100%——所有回傳結果的三個受控航段皆不落在
  使用者複選的月份內。
- **SC-008**: 行動裝置瀏覽器可完成「檢視結果、點開外部連結」兩項操作。
- **SC-009**: 使用者無需訂閱任何付費服務即可完整使用本功能。

## Assumptions

- **單一使用者**：本功能為個人工具，無多使用者、角色分層或分享需求，
  故不含權限控制。
- **只查價不訂票**：系統不介入訂票或付款，因此無不可逆操作、無冪等或補償需求。
- **樞紐固定**：四段票的轉機樞紐為使用者所在地機場，非可變參數。
- **外部查價服務有速率限制**：確切上限未經長期驗證，系統採保守設定並將該值
  標示為推估。
- **接駁票為估算**：以單一代表日期估價，不隨各組合日期逐一查詢，
  以避免查價量倍增。
- **達標通知不屬本規格**：目標價欄位在本規格中僅儲存，不觸發通知；
  通知行為屬 `flight-price-tracking`（handoff order 2）。
- **沿用既有查價能力**：本功能不重新實作查價與行程枚舉演算法，
  沿用專案內既有且已測試的模組。
- **沿用既有資料層慣例**：資料以獨立儲存體保存，不與其他領域資料共用。
- **貨幣單一**：僅支援新台幣；對外服務若要求 ISO 代碼，由實作層轉換，
  使用者介面一律顯示 NTD。
