# Phase 1 Data Model: 機票價格追蹤與通知

**Feature**: 006-flight-price-tracking
**Date**: 2026-09-23
**Storage**: 沿用 005 建立的 `poc/data/flights.db`，**不新增資料庫**

## 變更範圍

只在既有 `flight_track` 表新增 4 個欄位。**不新增任何資料表**。

```text
flight_track（既有）
  ＋ scan_frequency_days     重掃頻率
  ＋ last_notified_at        上次通知時間
  ＋ last_notified_price     上次通知時的價格
  ＋ last_notify_failed      上次通知是否送達失敗
```

---

## 新增欄位

| 欄位 | 型別 | 說明 | 驗證規則 |
|---|---|---|---|
| `scan_frequency_days` | INTEGER | 重掃間隔天數。預設 7（每週一次，PO 於 Q-017 決定） | 正整數；介面提供的選項需反映速率上限（見下方「為何不提供更高頻」） |
| `last_notified_at` | TEXT NULL | 上次成功送出通知的時間（ISO 8601） | NULL 表示從未通知過 |
| `last_notified_price` | INTEGER NULL | 上次通知時的最低四段票價（NTD） | 去重判定的依據，見下方 |
| `last_notify_failed` | INTEGER | 上次嘗試通知是否失敗（0／1） | 供介面標示「通知未送達」（FR-019） |

### 為何存 `last_notified_price` 而不只存時間

FR-009 要求「不重複通知，除非出現**比上次通知時更低**的價格」。
只存時間無法區分「價格真的更好了」與「只是又跑了一輪」——使用者要嘛
錯過更低的價格，要嘛被沒變的價格一直打擾。存下當時的價格才判定得出來。

### 為何不提供更高的重掃頻率

外部查價服務有速率上限（005 實測：52 與 205 筆/小時皆被阻擋，目前保守
設 20 筆/小時且該值為推估）。一個含 2 外站 × 8 日期的條件就是 16 筆，
已接近單小時上限。每日重掃多個條件會持續貼著上限跑，提高被阻擋的機率，
而機票價格也不至於每天劇烈變動到需要天天查。

## 不新增「排程執行紀錄」表

spec 的 Key Entities 提到排程執行紀錄。**決定以 launchd 的 log 檔承擔
這個角色**（`~/Library/Logs/alphavibe-flight-tracking.log`），不建資料表。

理由：該資料的唯一用途是人工排查「那天到底跑了沒、結果如何」，沒有任何
查詢或關聯需求；而既有排程（`market_scan`、`us_stock_scan`）也都是寫 log
不寫表。建表要付出 schema、清理策略與測試的成本，換不到對等的價值。

UI 需要的「上次成功時間」「下次預定重掃」都能從 `flight_track` 既有與
新增的欄位算出，不需要執行紀錄表。

---

## 排程選取邏輯（不落地，純計算）

「今天要重掃哪些條件」由排程腳本即時計算，不預先寫入資料庫：

```text
今天輪到  ＝ (track.id % 7) == 今天星期幾
週期已滿  ＝ last_success_at 為空，或距今已滿 scan_frequency_days 天
要重掃    ＝ 今天輪到 且 週期已滿
```

以 `id % 7` 決定星期幾，讓同一條件每次都落在同一天、不同條件盡量分散，
且新增條件不需重算全體（`research.md` §2）。

「下次預定重掃」同樣是算出來的：從上次成功時間加一個週期，再往後找到
第一個符合 `id % 7` 的日子。

## 與 005 既有欄位的關係

| 既有欄位 | 本功能的用法 |
|---|---|
| `target_price` | 005 只儲存不使用；本功能作為達標判定的門檻 |
| `last_success_at` | 005 已記錄；本功能用於「週期是否已滿」與過期判定 |
| 掃描結果表 | 唯讀：取最低價（`status='ok'`）作為達標判定的依據 |

**達標判定只看 `price`（四段票價），不含 `connector_price`（接駁估價）**
——PO 於 Q-016 決定，理由是接駁價為估算值且會變動，納入會讓通知時定時不定。

---

## 遷移

既有 `flight_track` 表需新增 4 個欄位。既有列的處理：
- `scan_frequency_days` 給預設值 7
- 三個通知相關欄位為 NULL／0（等同「從未通知過」）

以 `ALTER TABLE ... ADD COLUMN` 逐欄新增並容忍「欄位已存在」的錯誤，
讓建表邏輯對新舊資料庫都成立。
