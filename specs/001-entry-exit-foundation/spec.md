## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查詢持股的真實損益 (Priority: P1)

PO 在對話中問「我這幾檔到底賺賠多少」，系統回傳每檔的損益金額與百分比，
且能區分「已經落袋的（已實現）」與「還在帳上的（未實現）」。成本用 FIFO
（先進先出）配對，不是把所有買進混在一起平均——後者遇到買過又賣過的
標的會失真。

**Why this priority**：這是本階段的核心價值，也是 2026-09-01 事故的直接
成因（當時只能人工拼湊 `get_trade_ledger` 與現價心算，過程中出錯）。
沒有這項，其他都是錦上添花。

**Independent Test**：對任一有完整買賣紀錄的標的呼叫查詢，把回傳的
已實現/未實現損益，與手動依 FIFO 規則從 `get_trade_ledger` 原始交易列
推算的結果比對，數字一致即通過。

**Acceptance Scenarios**：

1. **Given** 某檔有多筆買進與部分賣出且買進量足以覆蓋賣出量，
   **When** 查詢該檔損益，
   **Then** 回傳已實現損益（賣出批次配對後的結果）、未實現損益
   （剩餘批次以現價計算）、以及各自的金額與百分比，並標明
   成本法為 FIFO、金額未扣交易成本。
2. **Given** 某檔的賣出股數超過流水表內的買進股數（既有部位在流水表
   起始日之前建立，無進場紀錄），
   **When** 查詢該檔損益，
   **Then** 回傳明確的「歷史不完整」狀態與缺口股數，不猜測缺失批次的
   成本、不輸出會誤導的損益數字。
3. **Given** 某檔目前沒有任何持股（已全數出清），
   **When** 查詢該檔損益，
   **Then** 仍回傳其已實現損益（不因為現在沒持股就查不到）。

### User Story 2 - 判斷現在的價位在歷史區間的高低 (Priority: P2)

PO 問「這檔現在的價位算高還是低」，系統回傳現價在該檔可得歷史收盤價
區間中的相對位置（百分位），並一併說明這個判斷是用多少樣本、涵蓋哪段
期間算出來的——讓 PO 知道這個數字有多少參考價值。

**Why this priority**：進場時機判斷的另一半。但受限於現有歷史資料深度
（見 Assumptions），本階段能提供的是「近期區間定位」而非「長期估值
定位」，價值低於 User Story 1，故列 P2。

**Independent Test**：對有足夠歷史資料的標的查詢，人工用同一段收盤價
序列計算百分位比對；對資料不足的標的查詢，確認回傳的是明確的「資料
不足」而非硬算出來的數字。

**Acceptance Scenarios**：

1. **Given** 某檔有足夠的歷史收盤價樣本，
   **When** 查詢其價位定位，
   **Then** 回傳現價的百分位、實際樣本數、涵蓋起訖日期。
2. **Given** 某檔的歷史收盤價樣本數低於可信門檻，
   **When** 查詢其價位定位，
   **Then** 回傳「資料不足，無法判斷」與實際樣本數，不輸出百分位數字，
   也不顯示 0% 之類會被誤讀為「在最低點」的值。
3. **Given** 某檔完全沒有歷史收盤價資料，
   **When** 查詢其價位定位，
   **Then** 明確回報無資料，且不影響同一次查詢中其他標的的結果。

### User Story 3 - 一次看完整個投資組合 (Priority: P3)

PO 問「我全部持股的損益狀況」，系統一次回傳所有標的的結果，不需要
逐檔問。資料有問題的標的（歷史不完整、缺股價）在同一份結果中標示
出來，不會讓整批查詢失敗。

**Why this priority**：便利性提升。單檔查詢（US1/US2）已能交付價值，
但 2026-09-01 事故正是發生在「一次分析 21 檔」的情境，批次能力能顯著
降低重蹈覆轍的機率。

**Independent Test**：對全部持股執行批次查詢，確認回傳筆數與逐檔查詢
結果一致，且其中至少一檔資料不完整的標的有被正確標示而非讓查詢中斷。

**Acceptance Scenarios**：

1. **Given** 投資組合中同時存在資料完整與資料不完整的標的，
   **When** 執行批次查詢，
   **Then** 每一檔都回傳各自的結果或明確狀態，任何單檔的資料問題
   都不會導致整批查詢失敗。

---

### Edge Cases

- **賣出量超過買進量**（實測 60 檔中有 21 檔如此，因流水表起始於
  2025-11-21，之前的既有部位無進場紀錄）：必須回報「歷史不完整」
  狀態與缺口股數，不得用猜測的成本補洞。
- **疑似重複的交易列**（實測有 141 筆同 code/action/股數/價格/日期的
  多餘列、3 組重複 order_ref）：會讓 FIFO 把重複列當成真實批次，
  算出偏離實際的成本與股數。
- **持股快照的均價欄位大量缺值**（實測最新快照 23 列中 21 列為空）：
  不能拿持股快照當 FIFO 的成本 baseline，也不能拿來交叉驗證。
- **標的沒有歷史股價快取**（實測僅 39 檔有，流水表 60 檔中 26 檔沒有；
  已出清標的通常不在刷新範圍內）。
- **交易成本未記錄**：流水表沒有手續費與證交稅欄位，損益只能是毛額。
- **股數單位**：流水表的股數欄位單位是「張」（實測值域 1–2000），
  換算金額時必須乘以每張股數，否則金額會差三個數量級。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系統 MUST 依 FIFO（先進先出）規則，將賣出交易與先前的
  買進批次配對，計算指定標的的已實現損益。
- **FR-002**：系統 MUST 以剩餘（未被配對掉的）買進批次與最新可得現價，
  計算指定標的的未實現損益。
- **FR-003**：系統 MUST 對已全數出清的標的仍回傳其已實現損益，不得
  因為目前無持股而查不到。
- **FR-004**：當某標的的賣出股數超過流水表內的買進股數時，系統 MUST
  回傳明確的「歷史不完整」狀態並指出缺口股數，MUST NOT 以推測的成本
  補足缺口後輸出損益數字。
- **FR-005**：系統 MUST 在回傳結果中明確標示成本法為 FIFO，以及
  損益金額未扣除交易成本（手續費、證交稅）。
- **FR-006**：系統 MUST 在偵測到疑似重複的交易列時提出警示
  [NEEDS CLARIFICATION: 疑似重複列（同標的/買賣別/股數/價格/日期）
  是否要在計算時排除，還是照原樣計入並僅附警示？]。
- **FR-007**：系統 MUST 計算並回傳指定標的現價在其可得歷史收盤價
  區間中的相對百分位。
- **FR-008**：系統 MUST 在百分位結果中一併回傳實際樣本數與涵蓋起訖
  日期，讓使用者能判斷該數字的參考價值。
- **FR-009**：當歷史收盤價樣本數不足以支撐可信的百分位判斷時，系統
  MUST 回傳明確的「資料不足」狀態與實際樣本數，MUST NOT 輸出百分位
  數字或任何會被誤讀為極端值的預設值。
- **FR-010**：百分位的區間長度
  [NEEDS CLARIFICATION: 現有歷史股價快取最長僅約 100 個交易日
  （約 4.7 個月，自 2026-04-13 起累積），無法支撐「近 52 週」或更長的
  區間。要 (a) 接受短區間並在結果中揭露實際涵蓋範圍，還是 (b) 改為
  線上查詢更長歷史（會增加外部 API 呼叫，與既有「頁面不即時查外部
  API」原則及額度風險衝突）？]。
- **FR-011**：使用者 MUST 能以單一次查詢取得全部持股的結果，且任何
  單一標的的資料問題 MUST NOT 導致整批查詢失敗。
- **FR-012**：以上查詢能力 MUST 可供對話助理直接呼叫取得結構化結果，
  不需使用者自行交叉比對多個既有查詢。
- **FR-013**：本階段 MUST NOT 修改既有的浮動損益顯示邏輯與其數值口徑
  （既有為加權平均、不扣賣出）；兩套數字並存期間，新結果 MUST 明確
  標注自己的成本法以免混淆。

### Key Entities

- **交易批次（Trade Lot）**：一筆買進形成的批次，含股數、單價、日期；
  賣出時依 FIFO 順序消耗批次。是已實現/未實現損益的計算單位。
- **標的損益結果（Position P&L）**：某標的的已實現損益、未實現損益、
  對應百分比、資料完整性狀態、成本法標注。
- **價位定位結果（Price Position）**：某標的現價的歷史百分位、樣本數、
  涵蓋起訖日期、資料充足性狀態。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：PO 詢問任一標的的損益時，能在一次查詢內取得結果，
  不需再人工交叉比對交易紀錄與現價（對照現況：2026-09-01 需要多輪
  對話與人工核算，且發生誤讀）。
- **SC-002**：對買賣紀錄完整的標的，系統算出的已實現損益與人工依
  FIFO 規則從原始交易列推算的結果 100% 一致。
- **SC-003**：所有資料不完整的情境（歷史不完整、無股價、樣本不足）
  100% 回傳明確狀態，不出現任何未標註的推測值或會被誤讀為極端值的
  預設值。
- **SC-004**：批次查詢整個投資組合時，單一標的的資料問題不會導致
  其他標的查不到結果。
- **SC-005**：PO 能從結果本身判斷數字的可信度（成本法、是否含交易
  成本、樣本數、涵蓋期間），不需回頭問「這個數字怎麼算的」。

## Assumptions

- **交易成本不納入**：流水表沒有手續費與證交稅欄位，本階段的損益一律
  為毛額。若 PO 要與券商對帳，需自行扣除交易成本。
- **股數單位為「張」**：依實測資料值域（1–2000）判定，金額計算需
  換算。
- **不修正既有資料**：疑似重複列、缺失的歷史交易、空白的持股均價
  都不在本階段修正範圍內（沿用既有「不回填/修正既有歷史」的決策），
  本階段只負責如實反映與警示。
- **現價來源沿用既有快取**：不為了計算損益而新增即時報價查詢。
- **百分位僅用收盤價**：歷史股價資料只有收盤價，無開高低與成交量。
- **不改既有顯示**：報告頁面的浮動損益維持現狀，階段B 才整合。
