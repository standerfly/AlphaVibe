# 原始素材：2026-09-01 對話——持股進場時機分析引出的功能缺口

來源：Claude Code 對話（AlphaVibe repo），PO 為 Stander。本檔案是當次對話的
整理紀錄與 Explore agent 查證結果，非事後改寫的需求文件——保留原始發現與
PO 口語判斷，供後續 pre-spec 萃取需求用。

## 觸發情境

PO 要求「分析我的投資進場時機，並給出後續建議」。執行方式是用
stock-researcher subagent 交叉比對既有唯讀工具：`get_holdings`、
`get_trade_ledger`、`get_stock_price_history`、`get_revenue_yoy`、
`check_position_control` 等，人工/agent 手動拼湊分析。

過程中發生的問題：
1. 第一輪分析把 `get_revenue_yoy` 回傳的 `yoy_growth` 欄位（原始小數，
   1.0=100%）誤當成已經是百分比直接顯示，導致「多數持股成長平弱」的
   結論方向整個錯誤（例如 3661 世芯-KY 實際年增率是 +181.78%，
   誤報成 1.82%；8299 群聯實際 +377.55%，誤報成 3.78%）。
2. 這個錯誤是靠 PO 事後要求「兩個都做」（更新現價＋重查YoY）、
   以及主線對話直接呼叫 `get_revenue_yoy` 原始 API 交叉核對才抓到的，
   不是系統自動擋下的。
3. PO 後來反問：「看來工具有不足」「除了工具以外，進出場的分析工具是不是
   也要追加開發？」——這是本次 pre-spec 的直接觸發點。

## 盤點結論（Explore agent 查證，2026-09-01）

已核對以下檔案:行號（供追溯，pre-spec 撰寫時可再次查證）：

### 已有但不等於「進出場時機分析」的既有工具

- `check_position_control`（`poc/kb-mcp/review_engine.py:454-547`）——
  整合信心分級初始部位（5/8/10%）、遞減式加碼比例
  （第1-5次40/25/15/10/10%）、單股/主題集中度警示（≥15%/≥50%）。
  是**部位大小/加碼節奏**建議，不涉及「現在這個價位算不算好的進場點」
  或任何出場判斷。
- `check_strategy_review`（`review_engine.py:302-349`）——重用
  `screener.screen_stocks()` 算好的PEG／回檔幅度／營收年增率，跟該策略的
  `invalidation`門檻比對。PO 已在 `roadmap.md:253-275`（2026-08-19~20
  的 1f+ PR-review化過程）明文寫下：「`check_strategy_review` 檢查的是
  『還符不符合當初篩選門檻』＝候選機制，不是持有／加碼條件」。
- `check_laoyutou_signal`（`review_engine.py:352-408`，MCP 工具定義在
  `server.py:484-486`）——查近N天（預設14天）「老芋頭」（PO信任的資深
  投資朋友／導師，真人非系統使用者，見`server.py:386`
  `save_laoyutou_trade` 的工具描述原文）的交易紀錄，比對PO是否持有
  該股，純陳述事實，刻意不做任何基本面判斷或建議。
- `_downside_risk`（`review_engine.py:146-200`，PE壓縮模型）——目前PER
  若高於近2年歷史90百分位（資料不足時退化用最大值×0.9），估算PE回歸
  歷史中位數的潛在跌幅%。**唯一一個做「現在的估值相對歷史區間高低位」
  的自動判斷，但衡量的是PER（估值倍數），不是股價本身相對歷史價格
  區間的位置**。
- `_growth_deceleration`（`review_engine.py:117-143`）／
  `revenue_yoy_accel`（`review_engine.py:984-1001`）——分別偵測「最近3
  個月月營收年增率仍為正、但連續下滑」與「最近兩期營收年增率加速」，
  範圍窄（只看2-3期），且已掛在模組D每日排程（17:00 launchd自動跑，
  `roadmap.md:200-208`），日常監控層面已部分自動化。
- 浮動損益顯示（`report.py:1922-1941`的`_chart_stats_html`；
  `app/routers/stock_detail.py:194-206`的`pnl_pct`）——用交易流水裡全部
  買進的加權平均價估算(現價-均價)/均價，只在個股詳情頁顯示單一時間點的
  快照數字。**這是PO手動做的「持股進場後損益」最接近的既有實作**，
  但只在個股詳情頁面顯示，不是MCP工具（無法被Claude對話直接查詢/
  彙整多檔），無歷史趨勢，非FIFO（不扣賣出，出清過的標的會失真）。

### 確認的 5 個缺口（PO這次手動做、現有工具沒覆蓋到）

1. **進場後損益追蹤**——沒有MCP工具化（Claude對話查不到）、非FIFO、
   無歷史趨勢、無跨標的彙總。
2. **現價 vs 歷史價格區間的相對高低位判斷（股價本身，非PER）**——
   `_downside_risk`的邏輯框架現成，但只套用在PER，沒有套用在股價
   序列上；`stock_price_history`表雖存了完整價格序列供圖表用，但沒有
   任何函式在其上做百分位/相對位置計算。
3. **停損/停利價位觸發判斷（相對PO自己的進場成本）**——完全沒有。
   策略層的`drawdown_pct`／`invalidation`門檻是相對市場波段高點或候選
   篩選門檻，不是相對PO自己的買入價；沒有任何函式讀`avg_cost`或
   `get_trade_ledger`的進場價去算「現在跌破成本X%該停損」或
   「漲了Y%該停利」。
4. **基本面訊號與價格背離的偵測**——`_growth_deceleration`（營收）與
   `_downside_risk`（PER）各自獨立運作，彼此不互相比對，也不跟股價
   走勢比對——沒有「營收轉強但股價不漲」或「股價漲但基本面未跟上」
   這類背離邏輯。
5. **營收年增率轉強/轉弱的自動觸發提醒**——部分覆蓋但範圍窄，見上。

### 相關但未兌現的既有規劃（不是全新想法，是舊決策被延後）

- **product-spec.md FR-051**（`product-spec.md:358-360`，通用檢視層
  定義）原文：「利多出盡（財報如預期兌現但股價無感，整合原FR-043
  錨點框架的**停利邏輯**／`framework_thesis_invalidation_exit`）」——
  規劃裡有寫要做停利邏輯，但對照程式碼，`general_review()`裡
  `good_news_priced_in`目前是`manual_notes`裡寫死的`None`，
  尚未自動化。
- **product-spec.md FR-022**（`product-spec.md:398-401`）：
  「記錄預計/實際進出場（價位、時間、理由）……不含Q-010排除的損益
  追蹤（邊界見SRC-009 OQ-2，2026-07-24已定案：損益統計留給交易覆盤頁
  階段再議）」——進出場紀錄的FR存在，但明文排除損益追蹤/統計，
  交易覆盤頁本身尚未規劃時程。
- **product-spec.md FR-011**（`product-spec.md:447-449`）：曾規劃
  「收盤價觸及entry_condition時報告標記買入提醒（SRC-001 §5）」——
  已明文放棄（entry_condition欄位實測0%使用），改稱由FR-052策略專屬層
  的門檻重新檢查頂替，但FR-052實際做的是「候選資格還成不成立」，
  不等同「現在該不該進場」。
- **product-spec.md FR-059**（`product-spec.md:451-460`，模組G策略
  績效回顧）：規劃「候選品質追蹤」「命中率vs誤判率」「跟老芋頭實際
  操作對照」，但這是策略/候選層級的**事後**回顧，不是個股進出場
  時機的即時分析，且目前樣本量不足尚未啟動（`roadmap.md:21`標記
  「⏳ 待樣本量足夠再啟動」）。

## PO 初步判斷（2026-09-01 對話中給出，非定案）

PO 認為值得追加開發，初步排序建議（決策支持階段給出，實際優先序與
每項具體規則都還沒定案，需要走完整 pre-spec 釐清）：

1. 進場後損益追蹤 MCP 工具化（FIFO 正確計算）——這次分析裡最花工、
   最容易兌現價值的一塊
2. 股價本身的歷史高低位判斷——可複用`_downside_risk`現成的邏輯框架，
   工程成本應該不高
3. 停損/停利觸發（相對PO自己的進場成本）——對應FR-051已規劃但未兌現
   的「利多出盡/停利邏輯」部分
4. 基本面與價格背離偵測——複雜度較高，建議前三項穩定後再做
5. 營收轉強/轉弱的完整趨勢判斷（擴大現有範圍）——可搭配1-2項一起做

PO 同時確認：這是新功能範圍，要走 ADR-0027 pre-spec 流程先定義清楚，
不是直接跳去改 `review_engine.py`。開放問題例如：
- 停損/停利門檻是固定百分比還是可設定？
- 損益追蹤要不要處理已出清標的（historical realized P&L）？
- 這些新工具是要新增MCP工具供Claude對話查詢、還是要整合進報告頁面
  (report.py/app/)、還是兩者都要？
- 跟既有的模組D每日排程（Layer 2立場記錄）是否要整合，或獨立運作？
