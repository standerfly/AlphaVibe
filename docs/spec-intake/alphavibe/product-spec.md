## 1. Overview（問題、目標與價值）

AlphaVibe 是台股為主、兼顧美股的個人投資知識庫與策略工作流（SRC-001
§1；2026-07-27 依 1b 實測經驗重新定義核心迴圈，見下方）。

- **問題**：投資資訊分散在 LINE、Email、Facebook、財經網站、YouTube，每日
  手動彙整約需 1 小時，耗時且易遺漏；且缺乏能長期累積、支撐選股與交易
  決策的個人資料庫（SRC-001 §1、§2；Q-001；SRC-009 §1）。
- **核心迴圈（2026-07-27 依 1b 實測重新定義）**：不是單一線性流程，是
  「策略引擎 ＋ 每日 PDCA」：
  1. **Plan／Do**：每天用已定義的投資策略（目前2套：PEG深度回檔＋集中
     持股、營收創高跌深補漲候選）自動篩選市場候選（模組C），並對觀察
     名單/庫存標的做檢視、產出下一步建議（模組D）
  2. **Check**：PO 檢視「今日重點」（值得留意的異動），對照老芋頭的
     實際交易動向交叉驗證
  3. **Act**：PO 自己判斷是否採納建議、更新立場；策略本身持續優化
     （不追求策略數量多，追求同一套策略不斷校準）

  這套迴圈是從 1b 實測資料反推出來的：實際使用模式是「批次持股健檢」
  ＋「批次候選篩選」＋「跟隨驗證老芋頭訊號」，不是原設計「逐檔資訊
  討論→浮現標的→估值→決策」的線性流程。
- **支援能力**：每日排程自動產出戰情室頁面（今日重點＋新候選＋觀察
  庫存總覽）；覆盤時間 1 小時 → 10 分鐘內的效率目標維持（SRC-001
  §1、§2；Q-029）。
- **引擎**：Claude 主力（聊天思考）＋ Cline 輔助（爬蟲等簡單工作），
  不自建內嵌 LLM 的產品；本地 SQLite 資料庫承載（Q-032）。
  **Q-034 後續更新（2026-07-27，1b評估結論）**：儀表板輸入需求以「對話
  輸入＋快速表單」（方案A）滿足，不需要服務化架構（FastAPI＋Agent
  Router＋多供應商）；local-first＋Claude Code對話的架構假設維持不變。
  **Q-046 再後續更新（2026-08-21 推翻 Q-034 與 Q-045，2026-08-22 完成
  上線）**：對外服務層改為 FastAPI（`app/`）＋ React（`web/`）輕量前後端
  分離（同源部署、單一 process，非完整雙服務分離，不需重新設計
  CORS／認證）；底層計算邏輯與資料庫（`poc/kb-mcp/`、SQLite）**未重寫**，
  `app/` 各 router 直接 import 既有函式。推翻理由與完整範圍見 §8、
  `docs/architecture.md`。
- **產品定位擴展（2026-08-21，Q-046）**：對外服務品牌名為 **STND**
  （個人遠端主控台；技術／repo 層級仍為 AlphaVibe），定位由單純投資
  工具擴展為「個人一站入口」多分頁主控台——除既有投資功能（儀表板
  分頁）外，新增**資產分頁**（已上線，見 FR-061）與**相簿分頁**（MVP
  僅導覽入口，見 FR-062），未來可能再擴充其他生活領域分頁（如旅遊，
  整合深度未定，見 §11 Q-047）。多分頁導覽外殼本身見 FR-060。
- **追溯性**：分析結論以快照凍結（當時價格／估值／引用來源／框架版本／
  產出模型），支援日後 diff——股市資料天生會過期，不凍結就是雜訊
  （SRC-010、Q-036）。**已知限制（2026-07-27）**：此機制（snapshots表）
  實測0筆使用，見§11。
- **即時性**：不要求即時（Q-003）。**優先級**：P0 核心工具（SRC-001 §2）。

### 老芋頭交易表（新增，2026-07-27，見FR-044）

老芋頭是PO信任的資深投資朋友／導師（非系統使用者，屬訊號來源，見§2）。
他的每日進出是目前最大宗的資料來源（84筆評論中64筆／76%轉貼自他），
且是策略引擎的重要輸入（觸發篩選＋交叉比對既有持股），值得結構化而非
停留在自由文字：

| 欄位 | 說明 |
|------|------|
| code, name | 股票代碼／名稱 |
| action | 買／賣 |
| shares, price | 股數／價格 |
| date | 交易日期 |
| reason | 原因（可為空，他不一定每次都寫；但寫的時候是重要訊號，`peg_deep_dip_concentration`策略本身就是從他寫的原因沉澱出來的） |
| source_ref | 來源引用 |

### 交易流水表（新增，2026-07-27，見FR-056）

已經加碼過幾次」。**正式取代/補強現行`holdings`快照覆蓋式的限制**

| 欄位 | 說明 |
|------|------|
| code, name | 股票代碼／名稱 |
| action | 買（含加碼次序）／賣 |
| add_sequence | 第幾次加碼（用於對照遞減比例40/25/15/10/10%） |
| shares, price, date | 股數／價格／日期 |
| source_ref | 來源引用 |

### 模組D檢視結果表（新增，2026-07-27，見FR-051~055）

## 4. User Scenarios 與驗收情境

### 場景 1 — 每日排程：策略篩選＋檢視（Happy Path，2026-07-27 依實際
使用模式重寫）

1. 每日 02:00，模組E排程依序觸發模組C（策略篩選引擎）與模組D（策略
   檢視引擎）。
2. 模組C套用目前2套策略的篩選規則，全市場批次掃描（近2000檔），產出
   當日新候選。
3. 模組D針對PO觀察名單＋庫存標的，跑四組成部分檢視：通用檢視層（財報
   兌現度/預期獲利上修/下檔風險/利多出盡/成長趨緩）、策略專屬層（各
   策略自訂門檻）、老芋頭動向比對、部位控制建議。
4. 檢視結果寫入模組D檢視結果表；若跟PO既有立場或其他策略的系統記錄
   衝突，標記衝突提醒（FR-055）。
5. PO開啟儀表板（方案A單頁），「今日重點」區塊優先顯示需要留意的
   標的，其餘正常顯示。
6. PO檢視後自行判斷是否採納建議、更新立場——系統只提醒，不自動決策。

**驗收**：排程執行後，模組D檢視結果表有當日記錄；儀表板「今日重點」
正確呈現觸發項目與部位控制建議數字；PO立場更新軌跡可追溯何者為系統
自動新增、何者為PO手動輸入（FR-051~055、FR-057、FR-058）。

### 場景 2 — 老芋頭訊號驗證（2026-07-27 新增，反映76%資料來源的實際
使用模式）

1. PO將老芋頭的每日進出貼入系統（結構化欄位：代碼/買賣/股數/價格/
   日期/原因）。
2. 系統依FR-044入庫老芋頭交易表，同時觸發模組D的老芋頭動向比對（不等
   排程，即時執行）：
   - 若他買入的標的符合PO的策略門檻，加入候選提示
   - 若他賣出PO持有的標的，交叉比對提醒（基本面是否支持這個動作）
3. PO自行查證基本面、決定是否跟進或保留自己的判斷。

**驗收**：貼入老芋頭交易後，相關標的立即出現在下次開啟儀表板的「今日
重點」；系統不會自動執行任何交易或立場變更，只產出提醒（FR-044、
FR-053）。

### 場景 3 — 對話式輸入（澄清：不是獨立儀表板UI，就是與Claude對話，
SRC-002；Q-019~Q-021）

1. PO直接在Claude Code（或手機Claude App透過遠端MCP，Q-037）與AI討論
   投資想法、貼入資訊、傳圖。
2. AI從對話中萃取可歸檔內容，即時提出「歸檔提議」：目標層級（L1/L2/
   L3）＋內容摘要。
3. PO對每筆提議選擇：確認入庫／修改後入庫／略過。確認後寫入對應層，
   附對話來源引用。
4. 變體（FR-018/FR-055）：萃取的個股立場與Layer 2既有立場（含系統
   自動記錄）矛盾時，提議卡標示「⚠️立場衝突」並列出既有立場，由PO
   決定是否更新。

**2026-07-27澄清**：原設計「儀表板切到AI對話輸入」的獨立UI從未實作
也不需要——對話式輸入的實際管道就是Claude Code本身；儀表板（模組F）
角色是呈現＋少數快速表單（方案A），不含聊天功能。

**驗收**：對話中提到個股看法時系統產生L2歸檔提議；未經確認不寫入任何
資料；確認後Layer 2出現該筆立場且source_ref指向該段對話；與既有立場
衝突時出現衝突標示。

### 場景 4 — 策略新增／調整（2026-07-27新增）

1. PO在對話中描述觀察到的操作邏輯或想法（自己的、或從老芋頭實際操作
   反推）。
2. AI協助整理成篩選規則＋策略專屬檢視規則，確認後寫入`frameworks.py`
   （或後續正式化的策略定義儲存）。
3. 系統重啟後新策略生效，自動納入模組C篩選與模組D檢視。

**驗收**：對話討論新策略後，PO確認的篩選門檻與檢視規則正確反映在下次
排程結果；不需要另外開發策略管理表單UI（FR-049）。

### 場景 5 — 例外流程（SRC-001 §6；2026-07-27擴充排程失敗處理）

- 外部API失敗（FinMind額度耗盡等）：報告標記「數據更新失敗」並用最後
  快取，不中斷生成；沿用`benchmark.py`已驗證的優雅降級模式（記錄
  error、不影響其他欄位、頁面顯示異常橫幅）。
- 模組D排程檢視失敗：不讓整份報告掛掉，該標的維持前一次檢視結果並
  標記「本次檢視失敗」。
- Vision解析不確定：報告標記「圖片解析不確定」，保留原圖連結人工核對。
- LLM抽取格式不符（如缺代碼）：片段移入「待人工確認」區，不寫入
  Layer 2。

**驗收**：模擬各失敗情境時報告仍能產出且含對應標記；「待人工確認」區
可見未通過格式檢核的片段。

### 內容項目狀態轉換（state model，維持不變）

已接收 → 已清洗（FR-012）→ 已抽取・待確認 → **已入庫**（使用者確認，
FR-003/FR-017）或 **已略過**；抽取格式不符 → 待人工確認區（場景5）。
模組D檢視結果狀態：排程/即時觸發 → 檢視中 → 完成（含衝突標記，見
FR-055）。

（`app/`）＋ React（`web/`）輕量前後端分離架構；底層計算邏輯與資料層
（`poc/kb-mcp/`）**未重寫**，完整架構見 `docs/architecture.md`。既有
模組 A-G 功能（含儀表板、市場掃描、5 個表單端點、MCP 連接器）全數
遷移到新架構，功能行為本身不變、僅遷移對外介面層——不重複列出獨立
FR，行為規格仍以 FR-001~059 為準（`/report-classic` 舊版頁面已停用
不遷移）。以下三條 FR 是本次擴建新增、原 FR 編號體系外的產品行為：

- **FR-060 STND 多分頁導覽外殼**：提供跨分頁共用的導覽列（首頁／
  儀表板／資產／相簿，未來可能新增），使用者可在分頁間切換；各分頁
  功能與資料統一收在同一個產品內，共用同一套服務與資料儲存（技術
  實作細節見 `docs/architecture.md`「分頁地圖」節，不在此複製）。
  **已上線**（2026-08-22）。
- **FR-061 資產分頁**：手動管理個人資產配置，無外部資料源串接，功能
  範圍：
  - 口袋（使用者自訂清單：名稱／目標金額／排序）
  - 帳戶（使用者自訂清單：名稱／類型標籤）
  - 口袋 × 帳戶金額記錄；刪除採封存不做硬刪
  - 建倉進度：10 月 checklist，每格可打勾／取消，打勾時輸入實際投入
    金額，寫入指定口袋 × 帳戶
  - 情境試算：起始本金／退休年齡／定期定額／報酬率 → 退休時資產、
    每月可提領金額，伺服器端即時運算不進資料庫。**已知限制**：年金
    公式精確版本尚未與 PO 核對，用範例反推目前有 1~2% 誤差，屬非阻塞
    開放項目（見 §11）
  - 不做對帳單匯入解析；需要更新資產資料時，透過同一套更新 API／未來
    MCP write 工具由 agent 協助寫入
  - 資料模型：全新 5 張表（口袋／帳戶／建倉進度／情境試算相關），
    詳見 `docs/architecture.md`「分頁地圖」節與
    `supporting-artifacts/2026-08-21-personal-console-expansion.md`
    「資產分頁設計」節
  **已上線**（2026-08-22）。
- **FR-062 相簿分頁（MVP 僅導覽入口，未含實際功能）**：目前僅有導覽列
  tab 與空白頁面（`Photos.jsx`），無對應後端 router、無資料表、無實際
  功能。**未來規劃**（尚未開工，非本輪承諾範圍）：參考使用者既有

## 7. Non-Functional Requirements（系統設計原則，SRC-001 §8）

- 穩定優於速度；速度以排程補足，不追求即時
- 最小化 LLM 請求；允許報告生成的兩階段呼叫（Q-015）
- 功能最小化、模組獨立開發測試後整合；介面（儀表板）與資料層分離
  （SRC-001「前後端分離」原則在 local-first 形態下的對應詮釋，Q-032）
- 架構文件完整維護，參數命名全系統一致
- 查證成本上限：單一標的單次查證 ≤ 3 個查詢；快照產生後優先讀庫、
  不重複查證（SRC-010 §6；Q-036）
- **策略引擎原則（2026-07-27新增）**：策略數量不追求多，追求同一套
  策略持續優化；模組D所有檢查結果是提醒不是自動裁決，決策權在PO
- **免責聲明**：系統輸出為研究輔助資訊、非投資建議；介面固定顯示此
  聲明（SRC-010 §6；Q-036）

## 8. Constraints & Assumptions

- **部署形態（Q-032修訂；Q-034／Q-045 於 2026-08-21 由 Q-046 推翻，
  2026-08-22 完成遷移並上線）**：對外服務（STND）現況為 **FastAPI
  （`app/`）＋ React（`web/`）輕量前後端分離**——前端 build 成靜態檔，
  與後端共用同一個 process／未來可 docker 化的單一 image，同源部署，
  不需要重新設計 CORS／認證，非完整雙服務分離。底層資料存取與商業
  邏輯（`kb_store.py`／`screener.py`／`report.py`／`frameworks.py`）
  **未重寫**，`app/` 各 router 直接 import 既有 `poc/kb-mcp/*.py`
  函式，`poc/kb-mcp/` 因此仍是查證計算邏輯的地方。AI 引擎（Claude
  聊天思考＋Cline 爬蟲粗活）與本地 SQLite 資料庫（`poc/data/
  alphavibe.db`）的組合維持不變，改變的只是對外服務層——不再是純
  local-first 常駐 script（原 `report_server.py`），而是具備多分頁
  擴充能力的服務化架構。**推翻理由（Q-046）**：為因應產品定位擴展為
  「STND 個人一站入口」多分頁主控台（新增資產、相簿分頁）帶來的未來
  功能擴充、維護性、docker 化需求，原本判斷「規格過剩」的服務化架構
  （Q-034）與「先打磨到常用才談架構升級」的排序（Q-045）不再適用；
  技術架構完整說明見 `docs/architecture.md`
- 依賴：SQLite 3（含 FTS5）、Claude（Claude Code／Desktop，含 Vision）、
  Cline、FinMind／Alpha Vantage API（SRC-001 §10 經 Q-032 修訂；注意
  本機實際為 Python 3.9.6）
- 不使用 Vector DB／embedding API（Q-015）
- **隱私**：LINE 群主知情同意；系統內外一律匿名顯示（Q-005）；
  僅收錄群主發言，群組其他成員發言不納入（Q-008）
- 初期單人使用；小規模朋友擴展屬未來範圍（SRC-001 §8）

## 9. Error Handling（產品層失敗行為；SRC-001 §9、§6 場景5；末行出自

| LLM 額度耗盡／逾時 | 該步驟失敗、已記錄 | 錯誤日誌＋通知使用者 | 切換備援模型或手動重跑 | 使用者 |
| 爬蟲被封鎖 | 該 URL 標記失敗 | 報告標記「抓取失敗」 | 建議手動貼入內容 | 使用者 |

| SQLite 鎖定 | 寫入暫停 | （自動處理） | 自動重試 3 次後記錄錯誤 | 系統；仍失敗記日誌 |
| AI 對話誤判歸檔內容 | 未寫入（確認制擋下） | 提議卡可修改／略過 | 使用者修改或略過（Q-021） | 使用者 |
| **模組D多重系統記錄衝突（2026-07-27新增）** | 記錄並存 | 畫面明確標示「這幾筆判斷互相衝突」 | 使用者自行判斷取捨 | 使用者 |
