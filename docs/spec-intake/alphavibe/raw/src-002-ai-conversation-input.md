# AlphaVibe — AI 對話式輸入需求 (SRC-002)

> 來源：2026-07-06 PO（Stander）於 Claude Code session 口述需求，
> 經三個產品決策問答確認方向（對應 clarification-log Q-019 ~ Q-021）。
> 本文件為原始需求素材，供 pre-spec 流程抽取；FR 編號為**候選編號**，
> 以 prespec 正式抽取結果為準。

## 1. 功能概述 (Feature Overview)

使用者希望在 AlphaVibe 儀表板中新增「AI 對話式輸入」：使用者以自然語言
與 AI 對話（討論投資想法、口述盤後心得），AI 從對話內容中萃取可歸檔的
資訊，依內容型態分類存入既有的三層知識庫。

原始需求語句（PO 原話）：
「我想要有一個 AI 跟我對話，然後把對話內容依照系統功能建立起來。」

## 2. 產品決策紀錄 (Product Decisions)

| # | 決策點 | 決定 | 對應澄清 |
|---|--------|------|----------|
| 1 | 功能定位 | 作為**第四種資料輸入方式**，與文字貼入、URL 爬取、圖片解析並列；不做全域投資助理（知識庫查詢對話），不做固定架構的盤後引導訪談 | Q-019 |
| 2 | 歸檔目的地 | 沿用**三層知識庫**：投資哲學 → Layer 1、個股立場 → Layer 2、盤勢/市場評論 → Layer 3；不按功能模組另建歸檔架構 | Q-020 |
| 3 | 入庫信任度 | **即時確認制**：AI 於對話中提議歸檔（目標層級＋內容摘要），使用者確認後才寫入；可修改或略過 | Q-021 |

## 3. 候選功能需求 (Candidate Functional Requirements)

> 編號接續 SRC-001 的 FR-001 ~ FR-014。

- FR-015: 使用者可在儀表板以「AI 對話」方式輸入資料：與 AI 以自然語言
  討論投資想法或口述盤後心得，作為與文字貼入（FR-001）、URL 爬取（FR-009）、
  圖片解析（FR-010）並列的第四種資料輸入方式
- FR-016: 系統可透過 LLM 從對話內容即時萃取可歸檔資訊，依內容型態分類：
  投資哲學/原則 → Layer 1；個股立場（{code, name, stance, reason, date}）
  → Layer 2；盤勢/市場評論 → Layer 3
- FR-017: 每筆歸檔提議須經使用者即時確認（確認／修改／略過）後才寫入
  知識庫；寫入內容附帶對話來源引用，支援報告的來源回溯（FR-007）
- FR-018: 對話中萃取的個股立場與 Layer 2 既有立場明顯矛盾時，沿用
  FR-013 的「⚠️ 立場衝突」機制：於提議卡片中標示衝突並列出既有立場，
  由使用者決定是否更新

## 4. 與既有需求的關聯 (Relation to Existing Requirements)

- FR-001（手動貼入）：本功能是輸入面的擴充，儲存時同樣依來源 tag
  （建議新增來源 tag：`conversation`）
- FR-003（LLM 抽取立場）：Layer 2 的抽取欄位與格式沿用 FR-003 的
  {code, name, stance, date}，本功能補上對話情境的 reason
- FR-007（來源回溯）：入庫內容需可回溯到對話片段
- FR-013（立場衝突標記）：衝突處理邏輯直接沿用，見 FR-018

## 5. 開放問題 (Open Questions)

- OQ-1: 對話歷史本身是否保存？只存「確認入庫」的內容，還是整段對話
  都留存（供來源回溯用）？保存多久？
- OQ-2: SRC-001 系統設計原則之一是「最小化 LLM requests」（Q-015），
  而對話式輸入天然增加 LLM 呼叫次數——v1 是否設定用量邊界
  （如每日對話輪數上限），或接受此功能為例外？
- OQ-3: 本功能是否納入 v1 MVP 範圍？（需 PO 於 scope-decision 定案）
- OQ-4: 「全域投資助理」（對話中可查詢知識庫既有內容）已決策本次不做，
  是否列入 Deferred（未來再考慮）清單？
