## User Scenarios & Testing *(mandatory)*

### User Story 1 - 登記待驗證判斷 (Priority: P1)

使用者在研究/分析對話中產生一個判斷或假設，附帶「等到某個未來時間點或
事件發生就能驗證」的但書。使用者請 Claude 把這個判斷登記下來，包含判斷
內容本身、觸發條件、以及預期驗證的時間點（或事件描述）。

**Why this priority**：這是整個功能的入口——沒有登記，後面的「被動提醒」
與「回頭驗證」都無從發生。這是 MVP 的最小可行切片。

**Independent Test**：可獨立測試——登記一筆項目後，直接透過查詢介面
（MCP tool）確認這筆記錄以 `pending` 狀態存在、欄位內容正確，不需要
依賴首頁顯示或標記解決功能。

**Acceptance Scenarios**：

1. **Given** 使用者有一個判斷「NVIDIA 2026/8/26 公布的 Q2 FY2027 財報，
   用來驗證漲價是否守住 75% 毛利率」，**When** 使用者請 Claude 登記，
   附上觸發條件（財報公布）與預期時間點（2026-08-26），**Then** 系統
   建立一筆 `pending` 狀態的待觀察記錄，之後可查詢到完整內容
2. **Given** 使用者嘗試登記一筆缺少判斷內容或觸發條件的項目，**When**
   呼叫登記操作，**Then** 系統拒絕寫入並回傳明確錯誤，說明缺少哪個欄位

---

### User Story 2 - 在 STND 首頁看到已到期的待驗證項目 (Priority: P1)

使用者打開 STND 首頁時，能直接看到「已到期」或「即將到期」但尚未驗證
的待觀察項目，不需要自己想起來要回頭查閱研究筆記。

**Why this priority**：這是本功能要解決的核心痛點——PO 在 NVIDIA 案例中
實際遇到「財報公布後，完全靠自己想起來才回頭查」的問題。這個使用者故事
把「登記」轉換成實際的產品價值。

**Independent Test**：可獨立測試——在資料庫中預先建立一筆 `trigger_date`
已過、狀態仍是 `pending` 的項目，直接開啟首頁確認該項目出現在對應區塊。

**Acceptance Scenarios**：

1. **Given** 一筆待觀察項目的 `trigger_date` 已過、狀態仍是 `pending`，
   **When** 使用者打開 STND 首頁，**Then** 首頁顯示這筆項目在「已到期／
   即將到期」區塊中，包含判斷內容與觸發條件摘要
2. **Given** 一筆待觀察項目的 `trigger_date` 還很遠（超過即將到期的
   判斷視窗），**When** 使用者打開首頁，**Then** 該項目不出現在首頁
   區塊中（但仍可透過查詢介面找到）
3. **Given** 首頁區塊查詢待觀察清單時發生錯誤（例如資料庫查詢失敗），
   **When** 使用者打開首頁，**Then** 首頁其餘內容正常顯示，該區塊顯示
   簡短錯誤提示，不影響首頁其他功能

---

### User Story 3 - 標記待觀察項目為已驗證，記錄結論 (Priority: P2)

使用者確認觸發事件已發生、判斷已經可以驗證後，請 Claude 把這筆待觀察
項目標記為已驗證，並記錄驗證的結論。

**Why this priority**：完成「判斷→觸發→結果」的完整軌跡，是這個功能
相對於「只提醒不追蹤結果」的加值之處，但即使沒有這一步，User Story 1+2
已經是可獨立交付的價值（使用者至少會被提醒，可以手動去別處記結論）。

**Independent Test**：可獨立測試——對一筆既有的 `pending` 項目呼叫標記
解決操作並附上結論文字，確認狀態轉為 `resolved`、結論與時間戳被正確
記錄，且該項目不再出現在首頁「待驗證」區塊。

**Acceptance Scenarios**：

1. **Given** 一筆 `pending` 狀態的待觀察項目，其觸發事件已發生，
   **When** 使用者請 Claude 標記為已驗證並提供結論文字，**Then** 該
   項目狀態轉為 `resolved`，結論與解決時間被記錄，且不再出現在首頁
   「待驗證」區塊中——但透過查詢介面仍可查得完整歷史記錄
2. **Given** 使用者嘗試標記一筆項目為已驗證但未提供結論文字，**When**
   呼叫標記操作，**Then** 系統拒絕這次狀態轉換並回傳錯誤，要求補上結論

---

### User Story 4 - 標記待觀察項目為不再追蹤 (Priority: P3)

使用者判斷某個待觀察項目已經不重要或不再需要追蹤（例如前提假設本身
已經不成立），請 Claude 將其標記為不再追蹤。

**Why this priority**：屬於清單維護的次要情境——沒有這個功能，使用者
仍可完成核心工作流（登記、被提醒、標記驗證），只是清單裡會累積一些
不再相關的項目。

**Independent Test**：可獨立測試——對一筆 `pending` 項目呼叫標記不追蹤
操作，確認狀態轉為 `dropped` 且不再出現在首頁區塊，但透過查詢介面仍可
追溯。

**Acceptance Scenarios**：

1. **Given** 一筆 `pending` 狀態的待觀察項目，使用者判斷不再需要追蹤，
   **When** 使用者請 Claude 標記為不再追蹤，**Then** 該項目狀態轉為
   `dropped`，不再出現在首頁「待驗證」區塊，但透過查詢介面仍可追溯

---

### Edge Cases

- 當一筆項目的觸發類型是「事件」（而非明確日期）且使用者未提供任何
  預估時間點時，系統如何判斷它算不算「已到期」？（見下方 Assumptions——
  預設做法是：沒有可比對的時間點時，此類項目不會自動出現在首頁「已到期」
  區塊，使用者仍可透過查詢介面找到所有 `pending` 項目）
- 使用者標記已驗證（resolved）卻嘗試不提供結論文字——系統應拒絕，見
  User Story 3 Acceptance Scenario 2
- 一筆判斷橫跨多檔股票或整條供應鏈（例如 NVIDIA 案例牽動記憶體/ODM/
  電力多個環節），系統如何呈現？——待觀察項目的股票代碼欄位是可選的，
  不強制綁定單一標的，也可以透過主題欄位分類
- 使用者想「撤銷」一次已標記為已驗證或不再追蹤的項目，回到待驗證狀態——
  系統不支援直接復原（這兩個狀態為終態），使用者需要登記一筆新項目來
  重新追蹤同一個判斷

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須允許登記一筆待觀察項目，必填欄位為判斷內容、
  觸發類型（日期或事件）、觸發條件描述；當觸發類型為「日期」時，
  觸發日期也是必填欄位
- **FR-002**: 系統必須在登記時缺少任一必填欄位時拒絕寫入，並回傳明確
  錯誤訊息說明缺少哪個欄位
- **FR-003**: 系統必須支援依狀態（待驗證／已驗證／不再追蹤）查詢待觀察
  項目清單
- **FR-004**: 系統必須支援查詢「已到期」的待觀察項目——即觸發日期已到
  或在近期視窗內（見 Assumptions），且狀態仍為待驗證
- **FR-005**: 系統必須允許將一筆待觀察項目標記為「已驗證」，此操作必須
  同時要求提供驗證結論文字，並記錄標記時間
- **FR-006**: 系統必須允許將一筆待觀察項目標記為「不再追蹤」，可選擇性
  附上原因說明
- **FR-007**: 一筆待觀察項目一旦被標記為「已驗證」或「不再追蹤」，狀態
  不可再改回「待驗證」（終態）；使用者若要重新追蹤同一個判斷，須登記
  一筆新項目
- **FR-008**: STND 首頁必須新增一個唯讀顯示區塊，列出「已到期／即將
  到期」且狀態仍為「待驗證」的項目，不含任何就地新增/編輯/標記解決的
  操作介面
- **FR-009**: 系統必須保留已標記「已驗證」或「不再追蹤」的項目供事後
  查詢回溯，不得刪除
- **FR-010**: 待觀察項目可選擇性關聯一檔股票代碼與／或一個主題，但不得
  強制要求恰好一檔股票——一筆項目可以橫跨多檔股票或不指定任何股票

### Key Entities *(include if feature involves data)*

- **待觀察項目（Pending Verification Item）**：代表一個附帶未來驗證
  條件的判斷或假設。關鍵屬性：判斷內容、可選的關聯股票代碼、可選的
  主題、觸發類型（日期／事件）、可選的觸發日期、觸發條件描述、可選的
  具體驗證目標（例如「毛利率75%」）、狀態（待驗證／已驗證／不再追蹤）、
  驗證結論或不追蹤原因、標記解決的時間、來源引用、建立與更新時間

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：使用者登記一筆待觀察項目後，能立即透過查詢介面找到這筆
  記錄的完整內容，不需要打開任何 markdown 檔案
- **SC-002**：一筆項目的觸發日期已過後，使用者下一次打開 STND 首頁時
  就能在對應區塊看到這筆項目，不需要自己想起來要回頭查閱
- **SC-003**：100% 已標記「已驗證」或「不再追蹤」的項目在標記後仍可透過
  查詢介面完整取回，沒有資料遺失
- **SC-004**：缺少必填欄位的登記請求 100% 被拒絕，且使用者能從錯誤訊息
  得知缺少哪個欄位

## Assumptions

- 首頁「即將到期」的判斷視窗期預設為 7 天（觸發日期在 7 天內或已過），
  這是可調整的實作細節，不影響功能範圍本身
- 觸發類型為「事件」且未提供觸發日期的項目，暫時不會自動出現在首頁
  「已到期」區塊（因為沒有可比對的時間點）——使用者仍可透過查詢介面找到
  所有待驗證項目，或後續補上一個預估日期讓它能被首頁判斷到期與否
- 本功能定位為個人使用（單一使用者），不涉及多人協作或角色權限
- 沿用既有知識庫（SQLite）與服務架構，作為一張新的獨立資料表，不修改
  既有的股票主題／評論／部位計畫等既有資料
- 首頁區塊為唯讀顯示，登記與標記解決一律透過使用者與 Claude 的對話
  （MCP tool）完成，不提供網頁上的新增/編輯表單（見 pre-spec 討論
  Q-003a，PO 已確認此範圍）
