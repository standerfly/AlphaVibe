## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新文章自動進文章庫 (Priority: P1)

PO 訂閱「定錨產業筆記」，文章只能登入會員網站後閱讀。網站發布新文章時會寄一封通知信到 PO 的
信箱（信裡只有標題與連結）。系統平常只檢查信箱；看到定錨的新信，才代 PO 登入網站、取得新文章的
全文與圖片存進文章庫，抓完立刻登出，並以 Telegram 告訴 PO 新文章的標題與連結。PO 完全不用動手，
也不必再手動複製貼上。

**Why this priority**: 這是本功能的核心價值，也是所有後續使用（搜尋、討論、表格數字）的資料來源。
同時它決定了對 PO 會員帳號的風險：存取必須低頻、不佔用登入名額。

**Independent Test**: 在信箱有一封定錨新文章通知信的狀態下執行一次，檢查文章庫出現該篇文章（標題、
日期、網址、全文、圖片齊全）、網站端不留系統的登入狀態、PO 收到一則含標題與連結的通知；立刻再
執行一次，新增 0 篇。

**Acceptance Scenarios**:

1. **Given** 信箱有定錨的新文章通知信，**When** 下一次排程執行，**Then** 該篇文章的標題、發布日期、
   網址、全文、內文圖片存入文章庫，PO 收到含標題與連結的通知。
2. **Given** 信箱沒有定錨的新信、也不是每週核對日、歷史回補已完成，**When** 排程執行，**Then** 系統
   不登入網站。
3. **Given** 某篇文章已在文章庫，**When** 它再次從通知信或清單被看到，**Then** 不重複開啟、不產生
   第二筆紀錄。
4. **Given** 某篇文章沒有通知信（漏寄或被歸類到別處），**When** 每週核對執行，**Then** 該篇被發現並
   匯入。
5. **Given** 清單上有標題以「【公告】」開頭的置頂文，**When** 系統讀清單，**Then** 該文不匯入。
6. **Given** 一次執行完成（不論成功或失敗），**When** 檢查網站端，**Then** 不留系統的登入狀態；PO 在
   手機與電腦間切換使用不受影響。
7. **Given** 待抓文章多於單次上限，**When** 執行，**Then** 只抓到上限為止，其餘留待之後的執行。

### User Story 2 - 在對話中搜尋與閱讀文章 (Priority: P2)

PO 在 claude.ai 或 Claude Code 與 LLM 討論投資時，可以請它用關鍵字（個股名稱、代號、產業詞）
搜尋已匯入的定錨文章，並讀取單篇全文作為討論依據。台股與美股兩個連接器都能查，查到的是同一批
文章。

**Why this priority**: 文章存起來是為了被用到；PO 明確要「先存全文，然後跟 LLM 討論」。沒有查詢
能力，匯入就沒有實際價值。

**Independent Test**: 文章庫已有數篇文章時，從台股連接器與美股連接器各以同一個個股名稱搜尋，兩邊
都得到相同的文章清單（含標題、日期、片段、原文網址），並可讀取其中一篇的全文。

**Acceptance Scenarios**:

1. **Given** 文章庫有提到「環宇-KY」的文章，**When** PO 以該名稱搜尋，**Then** 得到這些文章的標題、
   日期、相關片段與原文網址。
2. **Given** 搜尋結果中的一篇文章，**When** PO 要求讀取全文，**Then** 得到完整內文，以及文中表格的
   轉寫文字（見 User Story 3）。
3. **Given** 同一個關鍵字，**When** 分別從台股連接器與美股連接器搜尋，**Then** 結果相同。
4. **Given** 關鍵字沒有任何文章符合，**When** 搜尋，**Then** 明確回覆查無結果，不回傳不相關內容。

### User Story 3 - 表格裡的數字也讀得到 (Priority: P3)

定錨文章裡的財測 EPS、本益比等表格是以圖片呈現的，而這些數字正是 PO 討論的重點。系統在匯入時
就把表格圖轉寫成文字存檔，讓表格內容可以被搜尋、可以在討論時取得；同時保留原圖，並標示轉寫文字
是機器產生的，PO 有疑問時可以回頭看原圖。

**Why this priority**: PO 明確表示「表格數字是重點」。只存內文段落時，LLM 看不到最關鍵的數字。排在
P3 是因為它建立在 P1（有文章）與 P2（查得到）之上。

**Independent Test**: 匯入一篇含財測表的文章後，以只出現在表格裡的個股代碼搜尋可找到該文章；讀取
該篇時得到表格的轉寫文字（標示為機器轉寫）且可取得原圖；抽查數字與原圖一致。

**Acceptance Scenarios**:

1. **Given** 一篇含財測表的文章已匯入，**When** PO 詢問表中某檔個股的財測 EPS，**Then** LLM 取得的
   資料含該表格內容，並標示為機器轉寫、可回查原圖。
2. **Given** 某個數字或個股代碼只出現在表格圖中，**When** 以它搜尋，**Then** 可找到該文章。
3. **Given** 某張表格圖轉寫失敗或無法辨識，**When** 匯入完成，**Then** 文章與原圖照常保存，該圖標記
   「未轉寫」，不以空白或猜測值充數；之後可補做轉寫而不需重新存取網站。
4. **Given** 上線前的抽查，**When** 以一批真實表格比對轉寫結果與原圖，**Then** 一致率達 PO 認可的
   門檻才採用目前的轉寫方式；未達則改用更準確的方式。

### User Story 4 - 歷史文章一次補齊 (Priority: P4)

功能上線時，會員專區已累積一批歷史文章。系統以小批次、分散多天的方式把它們全部補進文章庫，中途
中斷（例如電腦關機）可以從未完成處接續，補完後這項工作就停止。

**Why this priority**: 歷史文章讓搜尋有完整的資料基礎，但它是一次性工作，且不影響新文章的匯入。
為了保護帳號，寧可慢慢補。

**Independent Test**: 啟動回補後觀察多次執行：每次抓取篇數不超過上限、中斷後下一次從未完成處繼續、
完成後與網站「總覽」清單逐篇核對無缺漏、無重複，之後回補不再執行。

**Acceptance Scenarios**:

1. **Given** 文章庫是空的，**When** 回補執行多天，**Then** 全部歷史文章（不分類，公告除外）都進入
   文章庫，與網站「總覽」清單逐篇核對無缺漏、無重複。
2. **Given** 回補進行到一半被中斷，**When** 下一次執行，**Then** 從未完成處接續，已存的文章不重抓。
3. **Given** 回補已完成，**When** 之後的排程執行，**Then** 不再進行回補。

---

### Edge Cases

- **登入失敗（密碼錯誤、帳號被鎖）**：當次中止、不重試，既有文章不變，PO 收到通知；PO 更新密碼後
  重新執行即可。
- **帳號因登入裝置數超限被停用**：當次中止，後續排程停止直到 PO 處理，PO 收到通知。
- **被網站阻擋的跡象**（連續逾時、拿到登入頁或非預期頁面）：整次中止，下一次執行至少延後一天，PO
  收到通知；不反覆重試。
- **單篇抓取失敗**：同一次執行不再嘗試該篇，下一次排程才重試；累計失敗達上限後停止自動重試並通知
  PO。其他文章不受影響。
- **頁面結構改變導致取不到內文**：該篇標記失敗，不寫入殘缺的全文，PO 收到通知與失敗清單。
- **信箱讀取失敗**：當次不觸發網站抓取；每週核對仍會補上漏掉的文章；連續失敗才通知。
- **單張圖片下載失敗**：文章仍保存，圖片標記為缺，下次執行補抓。
- **清單上的日期不可靠**（置頂公告的日期在未來、週報日期可能晚於實際發布日）：新舊與是否已抓，只以
  文章本身的身分判斷，不以日期判斷。
- **同一篇文章有多封通知信，或完全沒有通知信**：都不影響去重與完整性。
- **PO 正在使用網站時排程執行**：排程避開 PO 常用時段，且每次跑完即登出，不佔用登入名額。

## Requirements *(mandatory)*

### Functional Requirements

**取得文章**

- **FR-001**: 系統 MUST 以 PO 的會員帳號自動登入定錨網站；帳號與密碼不得出現在版本庫、對話或
  日誌中。
- **FR-002**: 系統 MUST 取得會員專區的全部文章，不依分類篩選、也不替文章分類；每篇取得標題、發布
  日期、網址、全文與內文圖片。
- **FR-003**: 系統 MUST 以文章本身的網址／文章 ID 作為唯一身分；重複執行，或同一篇文章從不同入口
  （通知信、清單）被看到，都不得產生重複紀錄，也不得重複開啟已匯入的文章。
- **FR-004**: 系統 MUST 略過標題以「【公告】」開頭的置頂公告。
- **FR-005**: 系統 MUST 以小批次回補全部歷史文章：每批有篇數上限，中斷後從未完成處接續，完成後
  不再執行回補。
- **FR-006**: 系統 MUST 以 PO 信箱中的定錨通知信作為新文章的觸發：平常只唯讀檢查信箱，有新信才
  登入網站；沒有新信的日子不登入網站。系統 MUST 另外每週一次核對網站清單，補上沒有通知信的文章。

**保護帳號與網站**

- **FR-007**: 低頻存取是硬性要求。系統 MUST 對每次執行的抓取篇數、每日執行次數、篇與篇之間的間隔
  設保守上限；歷史回補寧可拉長到數週也不得加速。上限的放寬須經 PO 同意。
- **FR-008**: 系統 MUST 在每次執行結束時登出、不保留登入狀態，並避開 PO 常用的時段，使 PO 的帳號
  不超過網站「同一帳號最多兩台裝置或瀏覽器上線」的限制。
- **FR-009**: 系統 MUST NOT 改變 PO 在網站上的資料（不留言、不加入最愛、不變更帳號設定）。文章因
  被開啟而變成「已讀」是 PO 接受的例外。
- **FR-010**: 文章內容僅供 PO 個人使用。系統 MUST NOT 讓文章內容經由無驗證的公開網址取得，也不得
  對外分享或再發布。

**失敗處理**

- **FR-011**: 登入失敗、被阻擋、頁面結構改變時，系統 MUST 中止當次執行、不刪除也不覆寫既有文章，
  並通知 PO。
- **FR-012**: 抓取失敗的文章，系統 MUST NOT 在同一次執行內重試，而是留到下一次排程；單篇累計失敗
  達上限後 MUST 停止自動重試並通知 PO。出現被阻擋的跡象時，系統 MUST 中止整次執行並把下一次執行
  延後至少一天。
- **FR-013**: 系統 MUST NOT 寫入殘缺的全文；取不到完整內文的文章標記為失敗，待之後重試。

**搜尋、閱讀與表格**

- **FR-014**: PO MUST 能在 claude.ai／Claude Code 對話中以關鍵字搜尋已匯入的文章，結果包含標題、
  日期、相關片段與原文網址；並能讀取單篇文章的全文。
- **FR-015**: 文章 MUST 存放在獨立的文章庫，不寫入台股或美股各自既有的資料；台股與美股兩個連接器
  MUST 都能唯讀查詢，且查到的是同一批文章。
- **FR-016**: 系統 MUST 在匯入時把文章內的表格圖片轉寫成文字並保存，使表格內容可被搜尋、可在讀取
  單篇時取得；轉寫文字 MUST 標示為機器轉寫，原圖 MUST 保留並可回查。
- **FR-017**: 表格轉寫失敗時，系統 MUST 把該圖標記為「未轉寫」，不得以空白或猜測值充數；之後 MUST
  能補做轉寫而不需重新存取網站。
- **FR-018**: 表格轉寫 MUST 採成本最低且準確度合格的方式：上線前以一批真實表格抽查轉寫結果與原圖
  是否一致，達 PO 認可的門檻才採用；未達則改用更準確的方式。

**通知**

- **FR-019**: 系統 MUST 在匯入新文章後以 Telegram 通知 PO，內容只含標題與連結，不含內文。
- **FR-020**: 系統 MUST 在需要 PO 介入的失敗（登入失敗、帳號停用、被阻擋、單篇達重試上限、頁面
  結構改變）發生時以 Telegram 通知 PO；通知與日誌不得包含帳號密碼、登入狀態或文章全文。

### Key Entities

- **文章**：一篇定錨會員文章。屬性：文章身分（網址／文章 ID）、標題、發布日期、全文、取得時間、
  處理狀態（已發現、已取得、失敗待重試、已放棄、已略過）、累計失敗次數。不含分類。
- **文章圖片**：文章內的一張圖。屬性：所屬文章、圖檔、是否為表格、轉寫狀態（已轉寫、未轉寫）、
  轉寫文字（標示為機器轉寫）。
- **通知信線索**：信箱中一封定錨通知信所指向的文章（標題與連結）。只作為觸發與待抓線索，不是內容
  來源，也不是文章的身分。
- **回補進度**：歷史回補做到哪裡、是否已完成。
- **執行紀錄**：每次執行的時間、觸發原因（新信、每週核對、回補）、抓取篇數、結果與是否已登出；
  用來驗證低頻上限與登出要求。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 歷史回補完成後，文章庫與網站「總覽」清單逐篇核對，缺漏 0 篇、重複 0 篇（公告除外）。
- **SC-002**: 上線後連續兩週，新文章遺漏 0 篇、重複 0 篇；每篇新文章在通知信寄達後一天內進入
  文章庫。
- **SC-003**: 沒有定錨新信的日子（且非每週核對日、回補已完成），系統登入網站的次數為 0。
- **SC-004**: 任何一次執行都不超過既定的低頻上限；每次執行結束後網站端不留系統的登入狀態（以執行
  紀錄 100% 驗證）。
- **SC-005**: 上線後 PO 的帳號未被鎖定、停用或限制存取。
- **SC-006**: 需要 PO 介入的失敗情境 100% 有通知，且既有文章沒有任何一篇因失敗而遺失或被覆寫。
- **SC-007**: 上線前抽查的表格，轉寫數字與原圖的一致率達 PO 認可的門檻；不一致或無法辨識者 100%
  有標示。
- **SC-008**: PO 以個股名稱或代碼搜尋，可在一次查詢內找到相關文章並讀到全文與表格內容，不需自行
  登入網站。

## Assumptions

- 使用者只有 PO 一人；排程在 PO 自己的電腦上執行，電腦關機期間不執行，開機後自動接續。
- 網站登入只需電子郵件與密碼，沒有驗證碼或雙因素驗證（依 PO 提供的登入畫面）。
- 網站條款允許基於個人使用目的瀏覽及下載；禁止散布與公開發表；同一帳號最多兩台裝置或瀏覽器
  上線，超過可停用帳號。PO 平常只在手機與電腦間切換、不會同時上線。
- 通知信的寄件者為 `postmaster@mailer.investanchors.com`，信內只有標題與連結；文章網址形態為
  `/user/vip_contents/<數字 ID>`，數字即文章 ID。
- 文章沒有附件或 PDF；內文是文字段落加表格圖片。
- 低頻上限的起始值：每次最多 5 篇、每日最多 2 次、篇間隔 30～90 秒隨機；單篇重試上限 3 次；被阻擋
  後下一次執行至少延後一天。技術規劃可調得更保守。
- 信箱讀取沿用專案既有的唯讀取信能力；通知沿用既有的 Telegram 通知能力。
- 表格轉寫需要可讀圖的模型服務，會產生少量費用；起始採用最低價位、抽查合格的模型。
- 清單上的日期與分類頁籤上的紅色數字不可靠，不作為新舊或篇數的依據。
- 不在本功能範圍：自動抽取個股立場或摘要、替文章分類、文章留言、STND 網頁閱讀頁、把表格數字
  逐格結構化成可計算欄位。
- 以下事項需在技術規劃第一步於 PO 的電腦上探查：清單是否分頁、歷史文章總篇數、登入狀態有效期、
  開啟文章是否改變已讀、通知信連結是否直指單篇文章。
