# Extracted Requirements: 機票查詢分頁（外站四段票掃描＋價格追蹤）

**Feature Slug:** flight-search
**Last Updated:** 2026-09-23

## Candidate Functional Requirements

| ID | 候選需求 | Source IDs |
|----|----------|-----------|
| CFR-01 | 掃描外站四段票（外站→台北→目的地→台北→外站），回傳按價格排序的結果 | SRC-001, SRC-005 |
| CFR-02 | **日期是輸出而非輸入**：使用者給時間範圍與行程天數，系統回傳「哪些日期便宜」 | SRC-001（「你找到便宜的機票，然後我再看時間是否適合」） |
| CFR-03 | 可指定候選外站清單（多選），且偏好可隨時改變、不得寫死 | SRC-001（「對成田的興趣大於沖繩」＋「目前啦」） |
| CFR-04 | 排除月份為 **1–12 月自由複選**，主行程與第1段各自獨立。不得寫死季節定義（南半球旺季與北半球相反） | SRC-001（「避開北半球的夏季」；PO 審閱 product-spec 後指正需通用化） |
| CFR-05 | 可設定第1段與第2段的間隔策略，支援拉遠到數個月 | SRC-001（「第一段與第二段是不是要隔4個月以上」「不用密集請假」） |
| CFR-06 | 系統自動為每個主行程日期挑選可行的第1段間隔（單一固定值無法同時滿足所有月份） | SRC-001＋SRC-005 第 21 節推導 |
| CFR-07 | 顯示台北→外站的自費接駁票估價，並計入總成本排序 | SRC-002（警語「需再買TPE-BKK單程機票」） |
| CFR-08 | 建立可持久保存的「追蹤條件」：目的地、外站、時間範圍、行程天數、間隔策略、目標價 | SRC-001（分頁範圍選 1+2） |
| CFR-09 | 依設定頻率自動重掃追蹤條件 | SRC-001（同上） |
| CFR-10 | 最低價跌破目標價時主動通知（Telegram，複用既有推播） | SRC-001（同上） |
| CFR-11 | 分頁開啟時直接顯示已查結果（不等待掃描） | SRC-001（「最小版：看結果＋手動觸發」） |
| CFR-12 | 可手動觸發單一追蹤條件重掃 | SRC-001（同上） |
| CFR-13 | 提供 Google Flights 原生價格追蹤的操作入口（僅主行程來回票可用） | SRC-001（「google flight也有票價變動提醒…讓我貼到網頁去執行」） |
| CFR-14 | 顯示掃描進度與速率限制狀態（含排隊筆數與預估時間） | SRC-005 第 20 節（速率上限導致大批掃描須跨時段） |
| CFR-15 | 提供每個結果的外部查價連結（四段票、接駁票） | SRC-001（PO 全程以連結核對實際航班） |

## Candidate Actors And User Goals

| Actor | 目標 | Source IDs |
|-------|------|-----------|
| PO／個人使用者（Stander，唯一使用者） | 不必手動逐一輸入日期，就能知道「哪個時段＋哪個外站」最便宜，再據此判斷請假可行性 | SRC-001 |
| 系統排程 | 定期重掃已建立的追蹤條件，並在達標時主動通知 | SRC-001 |

本功能為**單人個人系統**，無多角色、無權限分層需求。

## Candidate Success Criteria

| ID | 候選成功標準 | Source IDs |
|----|-------------|-----------|
| CSC-01 | 使用者不需輸入任何具體日期，即可取得按價格排序的日期建議 | SRC-001 |
| CSC-02 | 金錢成本為零（不訂閱付費 API） | SRC-001（「不要花錢」） |
| CSC-03 | 系統找出的組合，其第1段與第2段間隔可達 3 個月以上，讓兩趟旅行分開請假 | SRC-001 |
| CSC-04 | 系統回報的價格與 PO 在 Google Flights 上人工核對的價格一致 | SRC-002~004 為驗證錨點 |
| CSC-05 | 手機可開啟並查看結果 | SRC-001（選擇 STND 分頁而非 CLI 的理由） |

## Candidate Constraints And Assumptions

| ID | 約束／假設 | 類型 | Source IDs |
|----|-----------|------|-----------|
| CON-01 | 不得產生金錢成本；付費 API 僅作為備援且需使用者自備 key | 約束 | SRC-001 |
| CON-02 | 查價走瀏覽器自動化，有速率上限（實測 52 與 205 筆/小時皆被擋），大批掃描須跨時段分批 | 約束 | SRC-005 第 20 節 |
| CON-03 | Skyscanner robots.txt 明確 `Disallow /transport/*`，**不得程式抓取**，僅可產生連結供人點閱 | 約束 | SRC-005 第 12 節 |
| CON-04 | Google Flights 的原生價格追蹤**不支援多城市行程**，四段票無法使用，僅主行程來回票可追蹤 | 約束 | SRC-005（2026-09-23 對照實測） |
| CON-05 | 第1段（外站→台北）不可 no-show，否則後三段全部失效——UI 必須明確提示 | 產品約束 | SRC-002 警語 |
| CON-06 | 僅經濟艙有意義；商務艙促銷艙多帶 `NOT PERMITTED ON MULTI-CITY`，多城市查詢會跳艙翻倍 | 約束 | SRC-005 第 3 節 |
| CON-07 | 各航空票規不同（長榮要求第1、2段24小時內轉機；星宇允許多段中停、一年內完成），拉遠間隔的可行性依航空公司而異 | 約束 | SRC-005 第 17 節 |
| CON-08 | 促銷艙 travel validity 常見 3 或 6 個月，可能限制間隔上限（實測 90/120 天未觸發，150 天未驗證上限） | 假設 | SRC-005 第 17–18 節 |
| CON-09 | 系統對外顯示的任何限制數字，必須標註是實測值或推估值 | 品質約束 | SRC-001（PO 質疑「這是你的猜測，還是有證據?」） |
| CON-10 | 外站偏好會隨時間改變，不可寫入程式邏輯，須為可調設定 | 假設 | SRC-001（「目前啦」） |
| CON-12 | 排除月份不得預設季節定義；季節快捷須標明所屬半球 | 領域規則 | PO 審閱指正（2026-09-23） |
| CON-13 | 貨幣統一 NTD；對外 API 用 ISO 代碼 TWD | 約束 | PO 追加（2026-09-23） |

## Candidate Error Or Failure Behavior

| ID | 情境 | 候選行為 | Source IDs |
|----|------|---------|-----------|
| CEB-01 | 掃描途中被目標網站軟封鎖（表現為連續逾時，非 captcha） | 連續失敗達門檻即中止該批，保留已完成結果，明確告知使用者原因與建議等待 | SRC-005 第 14 節 |
| CEB-02 | 掃描中途當機／被中斷 | 已完成的每一筆都必須已落地，重跑時接續未完成部分，不重查已完成者 | SRC-005 第 15 節 |
| CEB-03 | 單筆查詢逾時（偶發，非封鎖） | 重試一次；若前一筆已失敗則不重試（被擋時重試必然也失敗，只拖長偵測時間） | SRC-005 第 15 節 |
| CEB-04 | 掃描量超過速率上限 | 不得直接失敗；應裁切為本時段可執行量並排隊其餘，顯示預估完成時間 | SRC-005 第 20 節 |
| CEB-05 | 查價成功但無任何可用票價 | 與「查詢失敗」區分顯示，避免使用者誤判為系統故障 | SRC-005（實測存在無結果但非錯誤的情形） |
| CEB-06 | 追蹤條件的自動重掃失敗 | 保留上次成功的價格與時間戳，標示資料已過期，不得以舊價觸發達標通知 | 推論自 CFR-09/CFR-10（待 PO 確認） |
