# Spec Kit Input: 進出場訊號層（門檻、背離偵測與主動提醒）

**Status:** Draft
**Source Product Spec:** ../../product-spec.md
**Source Scope Decision:** ../../scope-decision.md
**Spec Feature Slug:** entry-exit-signals
**Handoff Order:** 2

## Feature Summary

在階段A（`entry-exit-foundation`）的損益與價位計算基礎上，補齊進出場的
「訊號層」：讓 PO 與 Claude 討論後為每檔持股設定停損/停利門檻並持續
監控、偵測基本面與股價走勢的背離、擴大既有營收年增率轉強/轉弱的判斷
範圍，並在訊號觸發時一併提出該檔持股的調整建議。訊號同時整合進報告
頁面與既有模組D每日排程，做到主動提醒而非被動查詢。

## Actors

- **PO（Stander，唯一使用者）**：與 Claude 討論並設定每檔持股的停損/
  停利門檻；接收訊號提醒與調整建議，作為部位調整決策的輸入。
- **Claude（MCP 工具呼叫者與門檻討論對象）**：協助 PO 討論門檻設定、
  查詢訊號狀態、在訊號觸發時提出調整建議。
- **模組D每日排程（系統自動觸發者）**：每日 17:00 自動執行訊號判斷並
  寫入 Layer 2 立場記錄。

## Problem and Goal

階段A 提供了損益與價位的計算能力，但這些數字本身不會主動告訴 PO
「該動作了」。目前系統完全沒有相對於 PO 自己進場成本的停損/停利判斷
（既有策略層的 `drawdown_pct`／`invalidation` 是相對市場波段高點或候選
篩選門檻，不是相對 PO 的買入價），也沒有把基本面訊號與股價走勢互相
比對的背離偵測（product-spec.md FR-051 規劃過「利多出盡」但
`good_news_priced_in` 至今是寫死的 `None`）。

目標是讓訊號主動浮現、且觸發時不只說「觸發了」，還要給出可選的調整
方向，取代目前 PO 想到才查、查到也只能自己判斷的狀態。

## In Scope

- 停損/停利門檻的**協作式設定機制**：由 PO 與 Claude 討論後逐檔設定
  （非固定公式、非系統自動計算、非 PO 單方設定），系統負責記住設定值
  並持續監控現價是否觸發
- 基本面訊號（營收年增率變化）與股價走勢的背離偵測
- 既有 `_growth_deceleration`（`poc/kb-mcp/review_engine.py:117-143`）／
  `revenue_yoy_accel`（`review_engine.py:984-1001`）的營收年增率轉強/
  轉弱判斷範圍擴大（現況只看最近 2-3 期）
- 訊號觸發時（停損/停利/背離）一併建議該檔持股接下來可以怎麼調整
  （例如：換股、部分減碼、對沖、續抱理由）
- 報告頁面（`report.py`／`app/`）整合，含既有浮動損益快照顯示改用
  階段A 的 FIFO 邏輯以確保數字一致
- 整合進既有模組D每日排程（`roadmap.md:200-208`，17:00 launchd），
  主動觸發提醒並寫入 Layer 2 立場記錄

## Out Of Scope

- FIFO 損益計算與股價歷史百分位計算本身（階段A 已交付）
- 自動下單／自動執行交易——訊號與建議皆為唯讀性質
- 更廣的主動策略/選股發現（例如整合 `screen_stocks`／`market_scan`
  主動比對「有沒有更好的候選標的」）——建議範圍僅限「觸發訊號當下、
  該檔持股怎麼辦」
- 老芋頭訊號的自動化解讀（維持既有邊界：純陳述事實，不做基本面判斷）

## User Scenarios

1. PO 與 Claude 討論後為某檔持股設定停損門檻，之後每日排程掃描到現價
   觸及該門檻時，主動寫入立場記錄並提示 PO；PO 於報告頁面與對話中都
   能看到這則提醒。
2. 系統偵測到某檔持股「營收年增率轉強但股價未跟漲」的背離訊號，主動
   提醒 PO，並附帶「可以考慮加碼/繼續觀察」等調整建議選項。
3. 某檔持股觸發停利門檻，系統除了標示「已達停利」，也一併列出「部分
   減碼」「換股」「續抱（理由：…）」等選項供 PO 參考決策，不自動執行
   任何交易。
4. 尚未設定停損/停利門檻的持股，在每日排程掃描與報告頁面顯示中明確
   標示「尚未設定門檻」，不會被誤呈現為「安全」或「已觸發」。
5. 每日排程遇到資料來源異常（例如 FinMind/TWSE 額度用盡），記錄錯誤、
   該次受影響欄位標為異常，不中斷整批排程、不影響其他檢查項目。
6. 訊號有觸發但因資料不足無法產生調整建議時，仍照常標示訊號本身，
   建議欄位標示「資料不足，需人工判斷」，兩者明確區分。

## Functional Requirements

- **FR-E03**：系統應提供機制讓 PO 與 Claude 討論後，為指定持股設定
  停損/停利門檻；系統需記住設定值並持續監控現價是否觸發；尚未設定
  門檻的持股需有明確的「尚未設定」狀態，不可誤判為「安全」或「已觸發」。
- **FR-E04**：系統應能偵測基本面訊號（營收年增率變化）與股價走勢之間
  的背離——例如營收轉強但股價不漲、或股價上漲但基本面未跟上。
- **FR-E05**：系統應擴大既有 `_growth_deceleration`／`revenue_yoy_accel`
  的營收年增率轉強/轉弱判斷範圍。
- **FR-E06**：當 FR-E03 或 FR-E04 的訊號觸發時，系統除了標示訊號本身，
  也要建議該檔持股接下來可以怎麼調整。範圍鎖定在觸發當下的該檔持股。
- **FR-E07b**：報告頁面（`report.py`／`app/`）整合，含既有浮動損益快照
  顯示改用階段A 的 FIFO 邏輯。
- **FR-E08**：以上判斷需整合進既有模組D每日排程，主動觸發提醒並寫入
  Layer 2 立場記錄，而非僅在 PO 主動查詢時才計算。

## Success Criteria

- PO 能透過對話跟 Claude 討論、設定某檔持股的停損/停利門檻，系統之後
  能持續監控並在觸發時主動標示。
- 訊號觸發時能主動出現在報告頁面與立場記錄，不需 PO 主動查詢才看得到。
- 訊號觸發時附帶具體可選的調整建議，不是只有「觸發了」三個字。
- 「尚未設定門檻」「資料不足」「已觸發」「未觸發」四種狀態在頁面與
  MCP 回傳中都明確可辨，不互相混淆。
- 報告頁面顯示的損益數字與 MCP 工具查詢結果一致（同一套 FIFO 邏輯）。

## Constraints and Assumptions

- 依賴階段A（`entry-exit-foundation`）的 FIFO 損益與歷史百分位計算能力。
- 門檻設定是協作式（PO 與 Claude 討論），需要新的資料儲存機制記住
  設定值，含「尚未設定」狀態的表示方式。
- 沿用既有資料源與模組D排程機制，不引入新的外部資料源。
- 沿用本 repo 既有慣例：Python 3.9 相容、poc 零外部依賴、繁體中文介面；
  失敗降級沿用 `benchmark.py` 模式與「算不出來就明講」三分狀態原則。
- FR-E06 的調整建議不涉及自動下單，維持唯讀建議性質。
- 與既有 FR-051（利多出盡／停利邏輯，`good_news_priced_in` 目前為
  `None`）是互補而非重複：FR-051 的質化描述可作為 PO 與 Claude 討論
  門檻或背離判斷時的參考依據。
