**Feature Slug:** substack-import
**Last Updated:** 2026-11-19（追加決定後修訂）
來源：SRC-001、SRC-002（含「追加決定」節）、SRC-003。「待規格」＝數值或細節 raw 未定，進 Spec Kit 階段補。

## 1. 批次處理原則（部分失敗政策）

- 以「作者」為單位獨立處理：一位失敗不影響他位。
- 以「文章」為單位寫庫：單篇寫入失敗只略過該篇並記錄，不回滾其他篇。
- 絕不留下半寫入的文章紀錄；圖片失敗不算文章失敗。
- 重跑安全：以 guid／URL 去重，重跑不產生重複。

## 3. 觀測

- 每次執行記錄：開始／結束時間、作者數、各作者 HTTP 狀態、新增篇數、略過篇數、缺圖數、補下載成功數、因最小間隔跳過的作者數（皆不含標題）。
- 健檢回報：上次成功時間、連續失敗作者、當日請求數、剩餘硬碟空間、`substack.db` 與圖片目錄占用量（只報現況，Q-011）。
- 告警管道：Telegram 固定文字。

## 4. 手動恢復與回滾

- 單次失敗：PO 以手動即時取得或手動重跑一次（RSS 輪詢不需逐次確認；涉及登入／鑰匙圈／消耗用量者仍須親自確認）。
- 資料回滾：`substack.db` 獨立，可整檔還原備份；因不動 `articles.db`，回滾不影響 010。是否納入備份待 Q-111。
- 停用：停用排程（launchd 卸載）即可停止所有自動請求；設定檔停用單一作者。
- 部署前備份：沿用「不部署前未備份」原則（SRC-001）。
