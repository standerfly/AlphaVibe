**Status:** In Review
**Feature Slug:** flight-search
**Function Branch:** function/flight-search
**Product Owner:** Stander
**TPM:** Stander
**Accepted At:** N/A
**Acceptance Evidence:** N/A

## Problem And Goal

**問題**：PO 想買便宜的長程機票，但目前必須手動逐一輸入日期去查價與比價。
外站四段票（外站→台北→目的地→台北→外站）能顯著壓低票價——PO 提供的
實例是台北↔布拉格從 44,794 降到 31,036——但它的價格同時受外站、日期、
各段間隔等多個變數影響，人工窮舉不可行。

**目標**：讓 PO 給出「想去哪裡、大概什麼季節、行程幾天」，系統回傳
**按價格排序的日期與外站組合**，PO 再據此判斷請假是否可行。

關鍵方向（SRC-001）：
> 「日期才是我最困擾的、需要你幫我解決的。我想要的是，你找到便宜的機票，
> 然後我再看時間是否適合。」

**日期是輸出，不是輸入。**

## Business Context And Priority

- Priority: 中。個人工具，非營收或對外承諾，但 PO 有實際購票需求（2027 年布拉格行程）
- Timing: 無硬性期限；PO 已可用 CLI 取得答案，分頁化是為了手機可用與持續追蹤
- Business value: 單趟省下約 1 萬台幣（實例：一般買法 44,794 vs 四段票 31,036）；
  並讓第1段成為另一趟獨立旅行的回程，避免密集請假

## Actors

- **PO／個人使用者（Stander）**：唯一使用者。建立追蹤條件、檢視結果、
  據此決定是否購票。本系統為單人個人工具，無其他角色。
- **系統排程**：依設定頻率自動重掃追蹤條件，達標時主動通知。

## MVP Scope

### In Scope

1. STND 新增「機票」分頁，手機可開啟
2. 追蹤條件的建立、列出、刪除
3. 外站四段票掃描（日期抽樣、按價格排序）
4. 第1段間隔策略，含「自動避開指定月份」
5. 接駁票估價顯示（不參與達標判定）
6. 分頁開啟直接顯示已存結果；可手動觸發重掃
7. 背景掃描：速率守衛、跨時段分批、進度顯示
8. 達標通知（Telegram）
9. 每筆結果的外部查價連結
10. 關鍵票規風險提示
11. Google Flights 原生追蹤的操作入口（僅主行程來回票）

### Out Of Scope

- 訂票與付款
- 多使用者、權限分層、分享
- 拆票自組（各段分開購買）
- Skyscanner 等站台的程式化抓取（robots.txt 禁止）
- 付費 API 訂閱（備援路徑需使用者自備 key）
- 四段票的 Google Flights 原生追蹤（該功能不支援多城市）
- 商務艙查詢

### Deferred

- 價格趨勢圖與歷史走勢
- 「現在該買了嗎」的建議邏輯
- 多目的地同時比較
- 票規自動檢核（目前僅文字提示）

## Functional Requirements

| ID | 需求 | 可測條件 |
|----|------|---------|
| FR-01 | 使用者可建立追蹤條件，欄位為：目的地機場、外站（多選）、出發區間（起訖年月）、行程天數、第1段提前策略、目標價、重掃頻率 | 建立後條件持久保存，重開分頁仍在 |
| FR-02 | 系統依條件在出發區間內**抽樣**日期，不要求使用者指定確切日期 | 使用者未輸入任何具體日期即可得到結果 |
| FR-03 | 掃描結果以價格排序呈現，每筆含：主行程起訖日、外站、四段票價、航空公司、第1段日期與提前天數 | 結果表可依價格排序且欄位齊全 |
| FR-04 | 第1段提前策略至少提供：不拉遠、約 3 個月、約 5 個月、自動避開指定月份 | 選「自動避開」時，所有結果的第1段皆不落在排除月份 |
| FR-05 | 系統為每個主行程日期**各自**挑選可行的提前天數（單一固定值無法同時滿足所有月份） | 同一次掃描中，不同主行程日期可有不同提前天數 |
| FR-06 | 可排除特定月份，主行程與第1段各自獨立設定 | 排除 6–8 月時，主行程與第1段皆不落在該區間 |
| FR-07 | 顯示台北→外站的接駁票估價，標明為估算值 | 每筆結果旁顯示接駁估價與「估算」標示 |
| FR-08 | 掃描以背景方式執行，使用者不需停留在頁面等待 | 關閉頁面後重開，掃描仍在進行或已完成 |
| FR-09 | 掃描量超過速率配額時，自動裁切為本時段可執行量並排隊其餘 | 顯示「已完成 N／M」與預估接續時間 |
| FR-10 | 已查過的組合不重複查詢 | 重跑同一條件時，已有結果的組合不再發出請求 |
| FR-11 | 可手動觸發單一追蹤條件重掃 | 點擊後狀態轉為 Queued 或 Scanning |
| FR-12 | 依設定頻率自動重掃；預設每週一次，多條件錯開到不同日 | 兩個追蹤條件不會排在同一天 |
| FR-13 | 最低**四段票價**跌破目標價時發出 Telegram 通知 | 通知含條件名稱、價格、日期組合、連結 |
| FR-14 | 追蹤條件超過 2 個重掃週期未成功更新時標示為資料過期，且**不得**以過期資料觸發通知 | 過期狀態下即使舊價低於目標價也不發通知 |
| FR-15 | 每筆結果提供四段票與接駁票的外部查價連結 | 連結可直接開啟並顯示對應行程 |
| FR-16 | UI 提示關鍵票規風險：第1段不可 no-show、僅經濟艙有意義 | 結果頁可見該提示 |
| FR-17 | 顯示滾動視窗內的查詢用量與剩餘配額，並標明限制值是實測或推估 | 用量資訊可見且附性質標註 |
| FR-18 | 提供 Google Flights 原生價格追蹤的操作說明與主行程連結，並說明四段票不支援 | 說明可見且連結正確指向來回票頁面 |

## Acceptance Scenarios

1. **建立追蹤並取得排序結果**：PO 建立「布拉格／成田＋沖繩／2027-04～2027-06／
   12 天／自動避開暑假／目標價 38,000／每週」，掃描完成後看到按價格排序的
   組合清單，每筆含主行程日期、外站、票價、第1段日期。
2. **日期為輸出**：PO 全程未輸入任何具體出發日，系統仍回傳可行日期建議。
3. **跨時段分批**：條件含 3 外站 × 8 日期（24 筆）超過單時段配額，系統完成
   本時段可執行量後標示「已完成 N／24，剩餘將於約 N 分鐘後接續」，
   下個時段自動續掃且不重查已完成者。
4. **避開夏季**：選「自動避開暑假」後，所有結果的第1段與主行程皆不落在 6–8 月；
   若某個主行程日期找不到可行的提前天數，該日期被跳過並說明原因。
5. **達標通知**：某次重掃後最低四段票價 37,265 ≤ 目標價 38,000，PO 收到
   Telegram 通知，內容含日期組合與查價連結。
6. **接駁票不影響達標**：四段票價 37,500、接駁估價 6,000（總成本 43,500）、
   目標價 38,000 → **仍觸發通知**（以四段票價判定）。
7. **軟封鎖中止**：掃描途中連續 3 筆逾時，系統中止本批、保留已完成結果、
   標示「偵測到連續逾時（軟封鎖）」並建議等待，**不繼續發出請求**。
8. **資料過期不誤報**：追蹤條件連續兩週重掃失敗，狀態標為過期；即使上次
   價格低於目標價，也不發出通知。
9. **中途中斷可接續**：掃描進行到第 8 筆時服務被重啟，重新觸發後只查
   第 9 筆之後的組合。
10. **原生追蹤限制說明**：PO 開啟「Google Flights 追蹤」說明，看到四段票
    不支援的說明與可用於主行程來回票的操作步驟與連結。

## API 行為

新增 `app/routers/flights.py`，屬本專案內部 API（無對外契約）：

| 端點 | 行為 |
|---|---|
| 列出追蹤條件 | 回傳條件、最新結果摘要、狀態、用量資訊 |
| 建立追蹤條件 | 驗證欄位，建立後回傳 id；不立即掃描（由觸發端點決定） |
| 刪除追蹤條件 | 連同其結果一併刪除 |
| 觸發掃描 | 非同步，立即回傳狀態；配額不足時回傳排隊資訊而非錯誤 |
| 查詢掃描進度與結果 | 回傳已完成筆數、總筆數、狀態、排序後結果 |

錯誤語意：配額不足與被封鎖**不是 HTTP 錯誤**，而是正常回應中的狀態值
——它們是預期的營運狀態，不是系統故障。

## 資料模型

三類資料，存於獨立 db 檔：

| 資料 | 內容 | 保留 |
|---|---|---|
| 追蹤條件 | 目的地、外站清單、出發區間、行程天數、提前策略、排除月份、目標價、重掃頻率、狀態、上次成功時間 | 永久，由使用者刪除 |
| 掃描結果 | 所屬條件、主行程起訖、外站、第1段日期與提前天數、四段票價、接駁估價、航空公司、查詢時間 | 每輪覆蓋最新值；歷史保留為非阻斷項（Q-018） |
| 查價快取 | 以行程組合為鍵的價格，跨追蹤條件共用 | 沿用既有快取機制 |

## Error Handling Requirements

| Failure Case | Expected Product Behavior | User/System Feedback | Recovery Path | Blocking? |
|--------------|---------------------------|----------------------|---------------|-----------|
| 單筆查價逾時（偶發） | 重試 1 次；仍失敗則標記該組合失敗，繼續其餘 | 該筆顯示查詢失敗，不影響其他結果 | 下輪重掃自動再試 | No |
| 連續逾時（軟封鎖） | 立即中止本批，保留已完成結果 | 「偵測到連續逾時（軟封鎖），已中止」＋建議等待時間 | 下個時段自動接續，或手動觸發 | No |
| 速率配額用盡 | 裁切為可執行量，其餘排隊 | 「已完成 N／M，約 N 分鐘後接續」 | 自動接續 | No |
| 掃描中途服務中斷 | 已完成結果已逐筆落地，不遺失 | 重開後顯示已完成部分 | 重新觸發，只查未完成者 | No |
| 查價成功但無可用票價 | 與查詢失敗區分記錄 | 「此組合查無票價」（非錯誤） | 下輪重掃 | No |
| 重掃連續失敗達 2 個週期 | 標示資料過期，**停止以舊價觸發通知** | 「資料可能已過期（上次成功：日期）」 | 手動觸發或等待下次排程 | No |
| Telegram 推播失敗 | 重試 2 次後放棄，不影響掃描結果 | UI 標示「通知未送達」 | 使用者自行於分頁查看 | No |
| 抓取路徑長期失效（網站改版） | 切換 SerpApi（若有 key）；否則停止自動掃描 | 「自動查價暫停」，仍提供外部連結 | 人工比價；待修復 | Yes（功能核心） |
